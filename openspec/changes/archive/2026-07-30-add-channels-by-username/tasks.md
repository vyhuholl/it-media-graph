## 1. The flood record learns a fourth command

- [x] 1.1 `db/models.py`: `CollectionCommand.ADD = "add"`. The docstring claims each command owns the quota-bearing method it spends — that stops being true here, since `add` and `resolve` both spend `contacts.resolveUsername`. Rewrite it to say what remains checkable: a method filed under a command that has no business spending it is still the regression the table exists to catch, and the pair `add`/`resolve` is now the one legitimate overlap
- [x] 1.2 Alembic revision, upgrade: `ALTER TYPE collection_command ADD VALUE IF NOT EXISTS 'add'`, and nothing else in the revision. **Corrected from the design's first draft**, which called for an `autocommit_block()`: `4bb75804d3cd` already added `metadata` this way and documents why none is needed — Postgres 16 runs `ADD VALUE` inside a transaction fine, and what it refuses is *using* the value before that transaction commits. The rule is therefore "this revision must write no row with the value", which it does not
- [x] 1.3 Same revision, downgrade: **deliberately empty**, matching `4bb75804d3cd`. Also corrected — the design first called for rebuilding the type and failing on rows that carry the value. That trades a revert that does nothing for a revert that can destroy real rate-limit evidence, to undo a change that took nothing away. An unused enum value costs nothing and strands nothing
- [x] 1.4 Verify on a scratch database whose name ends in `_test`, never the working one. Read `alembic upgrade --sql` first. Then upgrade, downgrade and upgrade again, confirming the value survives a round trip and a re-run of the upgrade is a no-op. **Done** on `itgraph_migration_test`, dropped afterwards: offline SQL is one `ALTER TYPE` and the version bump, nothing that writes the value; after upgrade the type reads `backfill, resolve, metadata, add`; the downgrade rolls the version back and leaves the value, as documented; the second upgrade is a no-op and lands on the same four members

## 2. Parsing the input, before anything is spent

- [x] 2.1 New module `src/itgraph/usernames.py` — pure, no Telethon, no database. Parsing does not belong in `tg/`, and this is the part that has to be right *before* the first request: a malformed entry at line 90 must be found without spending 89 lookups
- [x] 2.2 `_parse_one(entry)`: accepts a bare username, a leading `@`, and `t.me` links in every form the existing link reader already handles. **Corrected** — the design assumed this module would define the parsing; `derive/references.py` already has `normalize_username` and `parse_tme_link`, and its docstring states the reason to reuse them: every username in the project crosses that one boundary so that a lookup and a `pending_mentions` key computed from the same handle agree. The module imports them and adds only what operator input needs
- [x] 2.3 What this module *does* add is the treatment of a bad entry. Derivation drops one silently, which is right for a stray path fragment in a message and wrong for a line someone typed on purpose: entries are refused by name with a reason, invite links named as invite links, and `t.me/c/<id>` links named for having no username to look up. **Corrected** — the design called for loose validation with no length band, on the grounds that Telegram has moved its own minimum. The project already enforces 4-32 with a leading letter and documents why (it is what rejects the reserved `s` and `c` segments); a list `add` accepted and `derive` would have dropped is worse than a rule that is one character too strict
- [x] 2.4 `read_entries(path)`: skips blank lines and `#` comments, parses each remaining line, and **collects every error before raising**, reporting them with the line number they carry in the file rather than among the entries. A file with three bad lines should take one run to find all three
- [x] 2.5 De-duplicate case-insensitively — parsing lowercases, so equal names are already equal strings — preserving first-seen order so a `--limit`-bounded run covers the same entries in the same order when repeated
- [x] 2.6 Tests in `test_usernames.py`: each accepted form normalises to the same name; invite links, id links, non-Telegram links and malformed entries are refused by name; a file with several bad lines reports all of them with correct numbers; comments and blanks are skipped; duplicates differing in case and form collapse to one, in first-seen order. One test asserts the error message's description of the rule against `normalize_username` itself, so the two cannot drift. 27 tests, green
