# itgraph
CLI-утилита для сбора и разметки базы айтишных телеграм-каналов: инвентарь, выкачка истории в сырой слой, граф репостов и упоминаний.

Все команды запускаются из корня репозитория. Обзор проекта — в [корневом README](../../README.md), карта модулей — в [CLAUDE.md](CLAUDE.md).

Порядок работы: `login` → `dump-dialogs` / `add` → `mark` → `backfill` → `metadata` → `derive` ↔ `resolve` → `affiliates` / `family`.

## Требования
- [uv](https://docs.astral.sh/uv/) — Python-окружением управляет он, `python` и `pip` напрямую не используются
- Python **3.14.3**, закреплён в `.python-version` точной версией. Не `3.14`: под такой запрос uv на машине без релизного 3.14 подставляет бету, а `pydantic` на `3.14.0b2` падает при импорте (`_eval_type() got an unexpected keyword argument 'prefer_fwd_module'`). Одинаковый интерпретатор на всех машинах — это то, ради чего пин вообще существует
- Docker (для Postgres)
- `api_id` и `api_hash` с [my.telegram.org](https://my.telegram.org)

## Установка

```bash
uv sync
cp .env.example .env   # заполнить TELEGRAM_API_ID и TELEGRAM_API_HASH
```

`TELEGRAM_API_ID` и `TELEGRAM_API_HASH` нужны только командам, которые подключаются к Telegram: `login`, `dump-dialogs`, `add`, `backfill`, `resolve`, `metadata`, `watch`. Без них настройки загружаются, остальное работает, а такая команда отказывается и называет обе настройки. Задать только одну из двух нельзя. `DATABASE_URL` нужен всем.

На хосте сбора каждый процесс получает только своё: у бота нет ни учётных данных Telegram API, ни ключей B2 и YouTube, а его `DATABASE_URL` указывает на его собственную роль.

### База данных

```bash
docker compose up -d          # Postgres на порту 5433
uv run alembic upgrade head   # накатить схему
```

Откатить схему на рабочей базе нельзя: `alembic downgrade` удаляет таблицы вместе с разметкой каналов, а URL берётся из окружения — то есть безопасная и разрушительная команды набираются одинаково. Поэтому откат разрешён только на одноразовой базе, чьё имя оканчивается на `_test`:

```bash
# посмотреть, что откат сделал бы, ничего не трогая
uv run alembic downgrade --sql head:base

# проверить миграцию на одноразовой базе
DATABASE_URL=postgresql+asyncpg://itgraph:itgraph@localhost:5433/itgraph_scratch_test \
  uv run alembic downgrade base
```

Если откат рабочей базы действительно нужен, сначала снимите копию (`make backup-full`), а затем разово выставьте `ITGRAPH_ALLOW_DESTRUCTIVE=1`.

### Резервные копии

Разметка каналов — это ручная работа, которую ничем не восстановить: канал можно перекачать заново, а решение «этот в скоуп, этот нет» нельзя. Поэтому копии снимаются двумя уровнями и **проверяются чтением** — файл, который не читается через `pg_restore`, копией не считается и не засчитывается.

| уровень | что | как часто | сколько хранится |
|---|---|---|---|
| `daily/` | `channels` + `backfill_state` + `yt_channels` + `yt_search_queries` | раз в 20 часов | 30 копий |
| `weekly/` | вся база, включая сырой слой Telegram | раз в неделю | все за 28 дней, но не меньше 4 копий |

В `weekly/` лежит и дамп, который снимает каждый `alembic upgrade`, поэтому полные копии хранятся по возрасту, а не по счёту: при счёте три миграции за день вытесняли все недельные копии (так было 1 ноября 2026). Четыре последние копии остаются, даже если старше 28 дней, — на случай, когда дампы долго не снимались.

YouTube-таблицы попадают в полный дамп целиком, как и все остальные: снимки счётчиков (`yt_raw_video_stats`) — временной ряд, который заново не скачать. Поисковые запросы (`yt_search_queries`) — твои слова и даты, поэтому они лежат ещё и в ежедневной копии рядом с разметкой.

Копии лежат вне репозитория: дамп содержит ваши подписки. На машине оператора это `~/itgraph-backups`; на хосте сбора — том `itgraph-backups`, который переживает удаление и пересоздание любого ворклоада неймспейса, базы включено (`BACKUP_DIR` указывает туда же). Имена в UTC с суффиксом `Z` — дамп, снятый в 13:08 по Москве, называется `...T100802Z`.

Утилиты PostgreSQL нигде не требуют установки на сам хост: на хосте сбора `pg_dump`, `pg_restore --list` и `psql` приходят из образа приложения и работают как локальные процессы против адреса из `DATABASE_URL`; на машине оператора они те же, но запускаются через `docker exec` в контейнер Compose.

Рядом с дампами каждый уровень держит симлинк на свой последний **проверенный** дамп — `weekly/full-LATEST.dump` и `daily/inventory-LATEST.dump`. Он нужен, чтобы восстановление и деплой называли путь, а не выбирали файл глазами: выбрать вчерашний дамп для переезда — значит потерять сутки снимков счётчиков, а их, в отличие от истории, не пересобрать. Симлинк относительный, поэтому переживает копирование каталога на другую машину.

```bash
make backup            # снять то, что назрело
make backup-full       # полный дамп прямо сейчас

make backup-install    # поставить агент launchd (раз в 4 часа)
make backup-status     # жив ли агент, с каким кодом завершился
make backup-log        # что он делал
make backup-uninstall  # снять агент; сами копии остаются
```

Агент запускается каждые 4 часа, а не в фиксированный час: на ноутбуке фиксированный час — это «когда крышка закрыта». Что именно снимать, решается по возрасту файлов на диске, поэтому лишние запуски ничего не стоят, а пропущенные из-за сна навёрстываются на следующем.

Кроме того, копия снимается автоматически перед каждым `alembic upgrade` на рабочей базе. Если копия не снялась, миграция не выполняется — обойти можно разовым `ITGRAPH_SKIP_BACKUP=1`.

Исключение одно: база, в которой ещё нет ни одной таблицы. Это первый `alembic upgrade` на новой установке — терять там нечего, а `pg_dump` пустой базы даёт архив без единой записи, который проверка справедливо считает несостоявшейся копией. Поэтому схема на чистой базе накатывается без дампа; одной таблицы достаточно, чтобы копия снова стала обязательной. На `make backup` это не распространяется: там пустая база — это и есть новость.

#### Восстановление

Процедуру стоит прогнать хотя бы раз — непроверенное восстановление копией не является.

```bash
# развернуть копию в отдельную базу и посмотреть, что в ней
docker compose exec -T postgres psql -U itgraph -d postgres \
  -c 'CREATE DATABASE itgraph_restore_test'
docker compose exec -T postgres bash -c \
  'cat > /tmp/r.dump && pg_restore -U itgraph -d itgraph_restore_test --no-owner /tmp/r.dump' \
  < ~/itgraph-backups/weekly/full-LATEST.dump
docker compose exec -T postgres psql -U itgraph -d itgraph_restore_test \
  -c 'SELECT status, count(*) FROM channels GROUP BY status'
```

Восстанавливать поверх рабочей базы имеет смысл только когда уже понятно, что именно потеряно: `pg_restore --data-only --table=channels` дольёт строки, не трогая схему.

##### На хосте сбора

Там копии лежат в томе `itgraph-backups`, а `pg_restore` есть в поде Postgres. Репетиция восстановления — одна команда в тестовом окружении: последний полный дамп, сверка строк каждой таблицы с дампом, миграция, убирающая людей из payload дампа, если он старше неё, нейтрализация копии и настоящие записи через работающий сервис (`deploy/runbook.md`, «Восстановление»).

Поверх рабочей базы — это путь, на который указывает роль, остановившаяся на базе с колонками без типов. Дамп идёт из пода с томом копий в под Postgres потоком, на самом хосте файлов не остаётся. Сначала остановить всех, кто пишет: коллектор, бота и все CronJob'ы.

```bash
scripts/on-host.sh --loop stop
ssh ВЫ@ХОСТ 'sudo k3s kubectl -n itgraph scale deploy/itgraph-bot --replicas=0'
ssh ВЫ@ХОСТ 'for job in $(sudo k3s kubectl -n itgraph get cronjobs -o name); do sudo k3s kubectl -n itgraph patch "$job" --type=merge -p "{\"spec\": {\"suspend\": true}}"; done'
```

Дамп читает короткоживущий Job с томом копий, тот самый, что `scripts/on-host.sh --backups`:

```bash
job=$(ssh ВЫ@ХОСТ "sudo k3s kubectl -n itgraph get configmap itgraph-console -o 'jsonpath={.data.backups\.json}' | sudo k3s kubectl -n itgraph create -f - -o name")
ssh ВЫ@ХОСТ "sudo k3s kubectl -n itgraph wait --for=condition=Ready pod -l batch.kubernetes.io/job-name=${job#*/} --timeout=180s"
ssh -T ВЫ@ХОСТ "sudo k3s kubectl -n itgraph exec $job -c itgraph -- cat /backups/weekly/full-LATEST.dump | sudo k3s kubectl -n itgraph exec -i statefulset/itgraph-postgres -c postgres -- pg_restore -U itgraph -d itgraph --no-owner --clean --if-exists"
ssh ВЫ@ХОСТ "sudo k3s kubectl -n itgraph delete $job"
```

Потом снять приостановку, `scripts/on-host.sh --loop start` и запустить роль: она проверит согласованность базы, домигрирует схему, если дамп старше кода, поднимет бота и проверит, что всё работает. `full-LATEST.dump` — последний **проверенный** полный дамп, а не последний вообще.

После восстановления из полного дампа YouTube-данные на месте: каналы, видео, снимки, история загрузок и записи о проходах. Восстановление из ежедневной копии возвращает только разметку и поисковые запросы; тогда названия каналов вернёт `itgraph yt refresh`, видео — ближайший `yt watch`, а историю — CronJob `itgraph-yt-backfill`, если проход включён (около 430 единиц квоты на 100 каналов и 2 140 на 500). Снимки, снятые до восстановления, в этом случае потеряны.

### Копии вне хоста

Копия на томе переживёт пересоздание любых ворклоадов, но не потерю самого хоста, поэтому каждая **проверенная** копия дополнительно уезжает с него — зашифрованной. Копия, не прошедшая чтение `pg_restore --list`, не уезжает: нечитаемый на месте архив вывозить некуда.

Проход запускается в конце каждого `itgraph backup` на хосте сбора и забирает каждую локальную проверенную копию моложе семи дней, у которой ещё нет копии в хранилище — инвентарную и полную одинаково, включая дамп перед миграцией. Временный отказ B2 — 408, 429, 500, 503 (например, `no tomes available`) или оборванное соединение — повторяется до пяти раз с новым адресом загрузки и паузами 1, 2, 4, 8 секунд, как велит документация B2. Неудачная загрузка не трогает локальные копии и их прунинг; она проваливает запуск с именем каждой незавезённой копии, и следующая попытка — на следующем запуске.

Хранилище — приватный бакет Backblaze B2, имена в нём `inventory/…` и `full/…`, с `.age` на конце, и никогда не используются повторно: новая копия не занимает место старой. Копия шифруется `age` на самом хосте, ключом-получателем `itgraph_backup_age_recipient` — он публичный; личность, парная ему, живёт только в менеджере паролей оператора, поэтому хост не может прочитать собственные копии. Ключ B2 на хосте умеет только добавлять файлы и перечислять имена (`listFiles`, `writeFiles`): удалить, перезаписать или скачать им копию нельзя. Хранение — забота хранилища, не наша: правила жизненного цикла прячут `inventory/` через 30 дней, `full/` — через 28 и удаляют на следующий день после скрытия; локальный прунинг копии в бакете не трогает. Денежные лимиты аккаунта стоят в $0 — выход за бесплатный тариф ломает загрузку (`cap_exceeded`), а не списывает деньги.

#### Восстановление из внешней копии

Прогоняется с машины оператора, где лежит личность `age`; для скачивания нужен ключ с `readFiles` — ключ хоста читать не умеет, и не должен.

```bash
# скачать копию из бакета (консоль B2 или `b2` CLI) и расшифровать своей личностью
b2 download-file-by-name <bucket> full/full-20261019T080000Z.dump.age /tmp/full.dump.age
age -d -i <файл-личности-из-менеджера-паролей> -o /tmp/full.dump /tmp/full.dump.age

# копия обязана читаться как архив — и побайтово совпадать с исходным дампом
pg_restore --list /tmp/full.dump | head

# развернуть в одноразовую базу, имя обязано кончаться на `_test`
docker compose exec -T postgres psql -U itgraph -d postgres \
  -c 'CREATE DATABASE itgraph_restore_test'
docker compose exec -T postgres bash -c \
  'cat > /tmp/r.dump && pg_restore -U itgraph -d itgraph_restore_test --no-owner /tmp/r.dump' \
  < /tmp/full.dump
docker compose exec -T postgres psql -U itgraph -d itgraph_restore_test \
  -c 'SELECT status, count(*) FROM channels GROUP BY status'
```

Сверьте число seed-каналов с числом на хосте сбора — это и есть проверка репетиции. После неё удалите `/tmp/full.dump*` и одноразовую базу.

### Авторизация в Telegram

Разовая операция. Сбор данных идёт через MTProto от лица обычного аккаунта, а не бота: Bot API не умеет читать историю каналов.

```bash
uv run itgraph login
```

Команда спросит номер телефона, код из Telegram и пароль двухфакторки, если он включён, и создаст файл сессии (`TELEGRAM_SESSION`, по умолчанию `itgraph.session`).

#### Если код не приходит

Для стороннего `api_id` Telegram присылает код **только сообщением в чат «Telegram»**, SMS не будет. Бывает, что сервер отвечает «отправлено», а сообщение так и не появляется — со стороны клиента это не чинится. Тогда есть вход по QR-коду, который обходит доставку кода целиком:

```bash
uv run itgraph login --qr
```

В терминале появится QR-код; на телефоне **Настройки → Устройства → Подключить устройство** → навести камеру. Токен живёт около полуминуты, команда перевыпускает его сама — сканировать нужно тот код, что сейчас на экране. Пароль двухфакторки, если он включён, спросят уже после сканирования. Результат тот же самый файл сессии, что и у обычного входа.

Не запускайте `login` повторно по кругу, если код не дошёл: неудачные попытки копятся на стороне Telegram и оборачиваются `FloodWaitError` на несколько часов.

**Файл сессии — это полный доступ к аккаунту.** Он в `.gitignore`; коммитить его нельзя ни при каких условиях. Все остальные команды только читают уже готовую сессию и никогда не спрашивают код: если сессии нет или она разлогинена, команда завершится с ненулевым кодом и отправит сюда.

## Прокси

Нужен на любом хосте сбора. Важен не «датацентровый адрес» сам по себе — Telegram в стране оператора заблокирован, так что аккаунт и сейчас ходит через коммерческий VPN, тоже датацентровый, и на этом собрал 211 тысяч сообщений за одиннадцать дней без единого лимита на пути сбора. Выделяется не датацентр, а **адрес, с которого больше никто не ходит**: у VPS собственный адрес используется ровно одной вещью, и эта вещь — коллектор. Поэтому нужен выход, разделяемый с живыми людьми: SOCKS5-эндпоинт VPN-провайдера, если он есть, или резидентный прокси.

На хосте сбора этот выход — не внешний эндпоинт, а xray-прокси внутри неймспейса (`itgraph-proxy`): SOCKS-вход с паролем внутри, наружу — ровно один исход, VPN-сервер, которым пользовался и ноутбук, чтобы при переезде Telegram не увидел смены адреса. У прокси нет `freedom` и запасного маршрута, поэтому недоступный выход рвёт соединение, а не уходит с адреса самого хоста; бот и YouTube при этом ходят напрямую — им адрес хоста не опасен.

Не задано — соединение прямое; рабочей конфигурацией это было на ноутбуке оператора, где адрес делился с живыми людьми.

```bash
PROXY_TYPE=socks5   # socks5 или http
PROXY_HOST=proxy.example.com
PROXY_PORT=1080
PROXY_USERNAME=     # необязательно
PROXY_PASSWORD=     # необязательно; не коммитить, как и api hash
```

Настройки читаются целиком: хост без порта, порт без хоста, логин без хоста или неизвестный тип — это ошибка при **загрузке настроек**, до того как что-либо соединится. Половинчатая конфигурация иначе всплыла бы часами позже, на машине, за которой никто не смотрит, и выглядела бы как баг коллектора, а не как опечатка в `.env`. На хосте сбора эти значения кладёт плейбук в Secret: `itgraph-proxy`, порт 1080, логин и пароль SOCKS-входа.

**Проксируется только MTProto.**

| команда | что делает | как ходит |
|---|---|---|
| `login`, `backfill`, `resolve`, `metadata`, `watch` | MTProto от лица аккаунта | через прокси |
| `bot` | Bot API поверх обычного HTTPS | напрямую |
| `derive`, `alerts`, `affiliates` | в сеть не ходят | — |

Бот не проксируется намеренно: у него нет риска бана, а лишний прокси на его пути — это лишняя точка отказа ради ничего.

**Запасного пути нет, и это главное решение здесь.** Недоступный прокси роняет команду с ненулевым кодом. Никакого `try` вокруг соединения, никакого повтора без прокси, никакой опции библиотеки, которая сделает это сама. Прокси, который молча падает на прямое соединение, хуже, чем его отсутствие: процесс работает, в логах всё зелёно, а аккаунт всё это время ходит с того самого адреса, который прятали. Функция безопасности, чей отказ выглядит как успех, превращает известный риск в неизвестный.

Цена принимается: сломанный прокси останавливает сбор. Цикл переживает остановку — одиннадцатичасовой простой это уже показал, пропущенный замер отбрасывается, а не догоняется, — так что час проблем с прокси стоит часа ранних кривых. Час непроксированного сбора стоит риска, который нельзя ни измерить, ни отменить.

Каким путём пошло соединение, видно в первой же строке лога:

```
INFO  itgraph.tg.client Telegram route: socks5 proxy at itgraph-proxy:1080
INFO  itgraph.tg.client Telegram route: direct, no proxy configured
```

Это единственный способ отличить проксированный деплой от того, куда не доехал `.env`: во втором случае всё работает, ничего не падает, и адрес неправильный. Пароль в лог не попадает никогда.

### Переезд на другую машину

**Файл сессии переносится, `login` заново не делается.** Это не удобство, а стоимость в днях сбора: `itgraph.session` — не только ключ авторизации, но и кэш peer'ов, из которого `backfill` и `metadata` берут `access_hash`. У свежей сессии его нет, поэтому все сид-каналы будут пропускаться (`skipped`) до тех пор, пока их не переберёт `resolve` — а он квотируется, пара сотен username в сутки. Подробнее: [файл сессии и что будет, если его потерять](#файл-сессии-и-что-будет-если-его-потерять).

Смена адреса у **уже авторизованной** сессии переавторизации не требует — это ровно то же, что переключение региона VPN, которое происходит и так. Подтверждение может спросить только **новый вход** с незнакомого места, то есть именно тот сценарий, которого здесь и не должно быть. `DEVICE_MODEL`, `SYSTEM_VERSION` и `APP_VERSION` при переезде не меняйте.

## Инвентарь каналов

Ничего нельзя собирать, пока нет списка каналов, с которых собирать. Список берётся из собственных подписок и размечается вручную.

```bash
uv run itgraph dump-dialogs   # импорт публичных подписок
uv run itgraph channels       # сводка по статусам + весь список
uv run itgraph mark <tg_id|@username> --seed|--maybe|--reject ...
```

Канал адресуется либо числовым `tg_id`, либо username — с `@` или без, регистр не важен. Если username по какой-то причине числится сразу за двумя каналами (старый владелец ещё не переимпортирован), команда откажется угадывать и попросит указать id.

В инвентарь попадает только то, что публично адресуемо: каналы и супергруппы с username. Личные диалоги, старые групповые чаты (тип `Chat`) и каналы без username пропускаются — команда печатает только их количество, без названий. Приватная переписка в базу не попадает никогда.

`dump-dialogs` идемпотентен: при повторном запуске он обновляет username и название канала, но не трогает разметку. Каналы не удаляются никогда — отписка от канала не убирает его из инвентаря, а отклонённые каналы остаются в базе: это размеченные данные для будущего классификатора кандидатов.

### Цикл разметки

```bash
uv run itgraph dump-dialogs
uv run itgraph channels --status candidate

# айтишный канал автора о себе — берём в сиды
uv run itgraph mark 1234567890 --seed --kind personal

# лента вакансий — то же самое по username
uv run itgraph mark @example_jobs --seed --kind vacancies

# не про айти — отклоняем, причина обязательна
uv run itgraph mark 1234567892 --reject --reason crypto --note "торговые сигналы"

# непонятно, вернёмся позже
uv run itgraph mark 1234567893 --maybe

uv run itgraph channels        # сколько осталось неразмеченных
```

Значения `--kind`: `personal`, `aggregator`, `company`, `vacancies`, `media`, `community`, `event`. Это то, чем канал **является**, а не то, о чём он пишет.

Значения `--reason`: `not_it`, `adjacent`, `crypto`, `infobiz`, `ads`, `content_farm`, `other_scene`. К любой причине можно добавить `--note` свободным текстом.

### Добавить каналы по имени

`dump-dialogs` берёт то, на что аккаунт подписан, `resolve` — то, что нашлось по ссылкам. Список каналов, о которых решение уже принято, добавляется третьей дверью:

```bash
uv run itgraph add @example_channel
uv run itgraph add --from-file channels.txt --limit 25
```

**Подписываться для этого не нужно, и никогда не было дешевле.** Чтобы открыть канал по имени, любой клиент всё равно тратит `contacts.resolveUsername` — тот же запрос, что тратит эта команда. Подписка добавляет сверху `channels.joinChannel`, то есть самый сильный сигнал бана из доступных, и ничего за это не покупает. Плюс тянет в инвентарь весь публичный список диалогов того аккаунта, с которого подписывались. `add` не вступает никуда и не читает список диалогов.

Формат файла — одно имя в строке; пустые строки и `#`-комментарии пропускаются, так что список можно вести с пометками. Принимаются `name`, `@name` и ссылки `t.me/name`, `t.me/s/name`, `t.me/name/123`. Инвайт-ссылки (`t.me/+…`, `joinchat`) отбиваются на разборе — они требуют другого метода и работают только там, куда аккаунт уже впустили. Все плохие строки сообщаются разом, с номерами, **до** первого запроса: ошибка в 90-й строке не должна стоить 89 лукапов.

Канал, который уже есть в инвентаре, не стоит запроса вообще. Это и есть механизм возобновления: прогон, остановленный на 60-м канале, продолжится с 61-го, если скормить ему тот же файл. `--limit` считает **запросы**, а не строки, — пропущенные бесплатны и бюджет не тратят.

Квота на `contacts.resolveUsername` — порядка двухсот в сутки, без батчинга, и делится с `resolve`. Сто каналов это примерно половина дневного бюджета, поэтому лучше несколькими заходами. Если по этому методу недавно прилетал лимит, команда скажет об этом перед стартом — но не откажется работать: `flood_events` записывает прогон, а не аккаунт за ним, а `add` как раз и рассчитан на запуск с другого аккаунта.

`--seed` и `--kind` работают только с именами в аргументах и отбиваются вместе с `--from-file`. Опечатка резолвится в того, кто держит неправильное имя, и с `--seed` уехала бы в скоуп, не показавшись человеку; список, который никто не перечитывал, — ровно тот случай. Для файла разметка остаётся обычной: `itgraph channels --status candidate`, потом `mark`.

Имена, которые не зарезолвились, печатаются в конце. `--failures-out failed.txt` дополнительно кладёт их в файл в том же формате, который читает `--from-file`, с причиной в комментарии — вход следующего прогона порождается, а не перенабирается. При нуле неудач файл не создаётся: пустой пришлось бы интерпретировать.

Разметку существующей записи `add` не трогает никогда — ни статус, ни kind, ни причину отклонения. Обновляется только username и название. Канал, отклонённый неделю назад и оставшийся в списке, останется отклонённым.

## Сбор истории

Разметка отвечает на вопрос, с каких каналов собирать. `backfill` собирает — выкачивает историю сообщений в сырой слой.

```bash
uv run itgraph backfill --since 2026-01-01
```

Сохраняется **payload целиком, как пришёл**, кроме того, что называет человека: аккаунты пользователей (последние комментаторы, платные реакторы, автор-пользователь, источник форварда), упоминания по id, подписи под постом и форвардом, списки id. Их `tg/payload.py` убирает до записи — поле становится `null`, элемент списка выпадает, каналы остаются. Ничего из этого не читается, а хранить чужие аккаунты незачем. Ничего не разбирается по дороге: репосты, упоминания, ссылки и язык вычисляются позже из этих же строк. Причина простая — разбор будет меняться много раз, а перекачивать историю ради исправления решения о разборе слишком дорого. Медиафайлы не скачиваются, сохраняются только метаданные из payload.

| опция | что делает | по умолчанию |
|---|---|---|
| `--since` | не запрашивать сообщения старше этой даты | обязательна |
| `--limit` | обработать не больше стольких каналов | все |
| `--delay` | опорная пауза между запросами, секунды | 4.0 |
| `--batch-size` | сообщений за запрос | 100 |
| `--max-messages` | не больше стольких сообщений с одного канала — никогда, `0` — без потолка | 2000 |

`backfill` не трогает описания каналов и связанные чаты — это отдельная команда [`itgraph metadata`](#метаданные-каналов), и разделены они не для порядка, а потому что стоят разного.

Потолок `--max-messages` ограничивает канал, а не запуск. Без него несколько крупных новостных агрегаторов, постящих десятки раз в день, займут бо́льшую часть базы — и это самые неинформативные вершины графа: они репостят всех, а их не репостит никто. Достигнув потолка, канал закрывается **насовсем**: обход останавливается, и следующие запуски к нему не возвращаются, даже с более глубоким `--since`. Потолок считается по строкам в сыром слое, поэтому собранное в прошлые запуски тоже идёт в зачёт. В отчёте такие каналы считаются отдельно, как `capped`, а в `cutoff_at` записывается дата самого старого реально сохранённого сообщения, а не запрошенная в `--since`.

### Осторожный первый запуск

Полный проход по 200+ каналам — это несколько тысяч запросов и **часы работы**. Это первая команда проекта, которая обращается к Telegram в объёме, поэтому начинать нужно с малого:

```bash
# два канала, неглубоко — посмотреть, что вообще происходит
uv run itgraph backfill --since 2026-06-01 --limit 2

uv run itgraph channels --backfill   # что получилось
```

Убедившись, что всё разумно, можно постепенно поднимать `--limit` и опускать `--since`. Прерывать команду безопасно: прогресс каждого канала сохраняется вместе с сообщениями, которые он описывает, в одной транзакции — следующий запуск продолжит с того же места, а не начнёт заново.

Значения по умолчанию намеренно медленные. Ускорять `--delay` без причины не стоит: лимиты Telegram считаются на аккаунт, поэтому спешка ничего не выигрывает, а выглядит как бот.

**Первый проход по всему инвентарю — это часы, но не дни.** Раньше здесь стояло «несколько дней»: каждый канал стоил двух запросов с суточной квотой ещё до первого сообщения, и проход по паре сотен каналов упирался в счётчик, который никакими паузами не сокращается. Теперь обход истории не тратит ни одного квотируемого запроса — `messages.getHistory` лимитируется всплеском, а не сутками, — поэтому ограничение здесь только время. Считайте по паре секунд на сотню сообщений плюс паузы между каналами.

Прерывать всё равно безопасно, и `--limit` никуда не делся: он полезен, чтобы посмотреть на поведение до того, как отпускать команду на весь инвентарь.

### Паузы

Пауза перед запросом не фиксированная. Она берётся случайно из полосы вокруг `--delay` (±50%, то есть `[2, 6]` секунды при значении по умолчанию), и изредка — примерно раз на пятьдесят запросов — вместо неё берётся длинная пауза 20–60 секунд. Между каналами берётся отдельная пауза 10–40 секунд — единственная граница в обходе, где паузы раньше не было вообще.

Стоит понимать, что чинит что. Случайность интервалов не уменьшает **число** запросов за сутки, поэтому на суточный счётчик она не влияет никак — это дешёвая маскировка, а не защита. Суточный расход снижает не она, а то, что квотируемых запросов в обходе больше нет: peer берётся из кэша сессии, а описания и связанные чаты ушли в [`itgraph metadata`](#метаданные-каналов). Плюс длинный `FloodWait` останавливает запуск вместо того, чтобы просидеть в нём сутки.

| настройка (`.env`) | что делает | по умолчанию |
|---|---|---|
| `pacing_jitter` | ширина полосы вокруг `--delay`, долей от него | `0.5` |
| `pacing_long_pause_chance` | вероятность длинной паузы вместо обычной | `0.02` |
| `pacing_long_pause_min` / `_max` | границы длинной паузы, секунды | `20` / `60` |
| `backfill_channel_pause_min` / `_max` | пауза между каналами, секунды | `10` / `40` |
| `flood_abort_threshold` | выше этого `FloodWait` запуск останавливается, а не пережидается | `1800` |
| `request_timeout_seconds` | сколько ждать ответа на **один запрос**, прежде чем бросить его | `180` |
| `channel_metadata_max_age_days` | сколько дней сохранённое описание канала считается свежим | `30` |

`request_timeout_seconds` ограничивает только сам запрос — ожидание лимита из него вынесено и по-прежнему не ограничено ничем. Значение обязано быть больше `flood_sleep_threshold` (Telethon пережидает короткий лимит **внутри** запроса), иначе настройки не пройдут валидацию.

Трогать их в обычной работе не нужно. Повод появляется после инцидента: получили длинный `FloodWait` — есть смысл поднять паузы между каналами; собираете каналы, которые часто меняют описание — опустить `channel_metadata_max_age_days`.

### Как читать состояние

```bash
uv run itgraph channels --backfill
```

Последняя колонка показывает, докуда дошёл сбор:

| значение | смысл |
|---|---|
| `-` | канал ещё не трогали |
| `running` | идёт сейчас, либо прошлый запуск прервали |
| `complete to 2026-01-01` | история собрана до этой даты |
| `skipped` | не собирали и не из-за ошибки: нет username, либо файл сессии не знает этого канала (см. [файл сессии](#файл-сессии-и-что-будет-если-его-потерять)) |
| `failed/permanent` | канал приватный, удалён или username больше не резолвится; повторно не запрашивается |
| `failed/transient` | сеть, таймаут, ошибка сервера; следующий запуск попробует снова |

Повторный запуск с той же датой пропускает уже собранные каналы. Запуск с **более ранней** датой не пропускает, а продолжает вглубь — поэтому окно можно расширять постепенно.

При `FloodWaitError` короче `flood_abort_threshold` (по умолчанию 30 минут) команда честно спит столько, сколько сказал Telegram, и повторяет тот же запрос. Другой сессии или аккаунта на этом пути нет ни в одной ветке: обход лимита — это то, что превращает ограничение в блокировку.

### Что делать, если запуск остановился сам

Ожидание длиннее порога не пережидается внутри процесса. Команда печатает обычный отчёт (это реально сделанная и уже закоммиченная работа), затем в stderr — сколько ждать и с какого момента можно продолжать, и завершается с кодом 1:

```
completed 34, capped 2, skipped 1, failed 0; 5120 new messages; 12 channels awaiting `itgraph metadata`
FloodWait of 86400s exceeds the 1800s halt threshold; stopping.
Work may resume after 2026-07-27 14:05 UTC.
```

Делать нужно ровно одно: дождаться названного времени и запустить ту же команду снова. Обход продолжится с сохранённого курсора, как после любого другого прерывания; канал, на котором всё остановилось, ошибочным не помечается и из будущих запусков не выпадает. Ненулевой код возврата нужен, чтобы остановленный запуск не выглядел успешным в расписании.

Последняя клауза отчёта — сколько каналов ждут `itgraph metadata`. Она печатается всегда, когда таким каналам есть чему быть, и считается из базы, без единого запроса.

Сутки ожидания на этой команде теперь означают что-то новое, а не привычную суточную квоту: обход истории квотируемых методов не трогает. Стоит посмотреть `itgraph floods` и понять, какой метод назван, прежде чем что-то менять в настройках.

### Что именно упёрлось

Каждое ожидание записывается в таблицу вместе с методом, который его вызвал:

```bash
uv run itgraph floods                      # всё, что накопилось
uv run itgraph floods --since 2026-07-01   # за период
```

Сначала идёт сводка по методам (сколько раз и максимальное ожидание), затем сами события. Сводка — это та форма, которая отвечает на вопрос «это то же самое, что в прошлый раз, или что-то новое».

Ради чего это заведено: у каждой команды теперь свой квотируемый метод, и колонка `command` — это то, что делает такое соответствие **проверяемым**.

| команда | что тратит | суточная квота |
|---|---|---|
| `resolve` | `contacts.resolveUsername`, `channels.getChannels` | да, и самая жёсткая — порядка пары сотен в сутки, батчей у неё нет |
| `metadata` | `channels.getFullChannel` | да |
| `backfill` | `messages.getHistory` | нет — лимитируется всплеском, ожидания секундные |

`ResolveUsernameRequest`, записанный под командой `backfill` или `metadata`, — это не курьёз, а регрессия: обе обязаны брать peer из кэша сессии, а не резолвить username. Именно ради этой проверки колонка и существует — по имени метода такое не увидеть.

Чего таблица **не** говорит:

- **Строка не доказывает, что запрос ушёл в сеть.** Telethon ведёт свой учёт ожиданий по методам и отказывает в методе, который ещё под ожиданием, — такой отказ приходит тем же `FloodWaitError`. Отличить его от настоящего лимита по самому исключению нельзя, поэтому таблица и не пытается: считать строки как потраченные запросы значит завышать расход.
- **Коротких ожиданий здесь нет.** Всё, что короче `flood_sleep_threshold` (60 секунд), Telethon пересыпает сам и до записи не доводит. А растущая частота именно коротких ожиданий — это ранний признак того, что троттлинг начался, и он отсюда не виден.

### Файл сессии и что будет, если его потерять

Канал адресуется по `access_hash`, который выдаётся **на каждый аккаунт свой**. В базе хранятся только `tg_id` и username; хэши живут в файле сессии, куда Telethon складывает их по мере того, как узнаёт о каналах — при `dump-dialogs`, при `resolve`.

`backfill` и `metadata` берут peer **только оттуда** и в сеть за ним не ходят. Это и есть то, что держит их вне суточной квоты, но у этого есть обратная сторона: канал, которого файл сессии не знает, будет **пропущен** — со статусом `skipped` и записанной причиной, — а не отрезолвлен по-тихому. Пропуск не помечает канал ошибочным и не выводит его из области сбора; следующий запуск с прогретым кэшем обойдёт его как обычно.

Практический вывод: потеря `itgraph.session` **не теряет данные**, но до `dump-dialogs` (для своих подписок) или `resolve` (для найденных по ссылке) обход будет пропускать каналы. Если очередной `backfill` вдруг отчитался о десятках `skipped` — смотреть надо сюда.

Резервных копий сессии не делайте: это полный доступ к аккаунту.

## Метаданные каналов

Описание канала и связанный чат обсуждений приходят одним запросом — `channels.getFullChannel`. Он не кэшируется, то есть это поход в сеть каждый раз, и у него **суточная квота**. Двести каналов — это двести квотируемых запросов, потраченных на то, чтобы перечитать описание, которое меняется раз в несколько месяцев.

Поэтому это отдельная команда, а не шаг обхода истории:

```bash
uv run itgraph metadata --limit 50
```

| опция | что делает | по умолчанию |
|---|---|---|
| `--limit` | запросить не больше стольких каналов | все, кому пора |
| `--delay` | опорная пауза между запросами, секунды | 4.0 |
| `--refresh` | перезапросить всех, даже тех, чьё сохранённое описание ещё свежее | выключено |

Свежесть считается по `channel_metadata_max_age_days` (по умолчанию 30). Канал, чьё описание моложе этого срока, команда молча пропускает; `--refresh` — это способ сказать «я знаю, что сохранённое врёт».

**Зачем разделять.** Пока метаданные запрашивались перед каждым обходом, запуск, упёршийся в их квоту, не собирал и историю — дорогой проход утаскивал за собой дешёвый. Теперь `metadata` может остановиться на первом же канале, а следующий `backfill` всё равно обойдёт весь инвентарь. Ровно это и проверяется тестом `test_a_halted_metadata_pass_leaves_history_collectable`.

Практический ритм: `backfill` — когда захочется, `metadata` — примерно раз в месяц. Первый проход по инвентарю удобно разложить на несколько заходов через `--limit`; остановка стоит только остатка этой очереди.

Забыть про команду сложно: `backfill` в конце отчёта печатает, сколько каналов её ждут.

```
completed 34, capped 2, skipped 1, failed 0; 5120 new messages; 12 channels awaiting `itgraph metadata`
```

Как и `backfill`, команда пропускает каналы, которых не знает файл сессии, вместо того чтобы резолвить их username: резолв — это [`itgraph resolve`](#resolve) и его бюджет. Ведёт себя при лимитах так же: короткий `FloodWait` пережидает, на длинном останавливается с кодом 1 и печатает, когда можно продолжать.

## Слежение в реальном времени

`backfill` собирает историю и заканчивается. `watch` не заканчивается: он опрашивает seed-каналы по расписанию, складывает новые посты в сырой слой и пишет **снимки метрик** — сколько у поста просмотров, репостов, реакций и комментариев в этот момент.

```bash
uv run itgraph watch
```

Снимки нужны потому, что `raw_messages` неизменяем по конструкции: первая загрузка сообщения выигрывает, и счётчик там жить не может. Каждое число просмотров в базе — это один замер, сделанный тогда, когда backfill дошёл до канала, на посте случайного возраста. Всплеск по одному замеру не виден вообще: 5000 просмотров — это много или мало, зависит от канала и от того, сколько посту часов.

### Один запрос делает два дела

`messages.getHistory` возвращает каждое сообщение со счётчиками **на момент ответа**. Поэтому одно окно свежей истории канала отвечает сразу на два вопроса: не появилось ли нового и что сейчас с уже известными постами. Стоимость — на канал за цикл, а не на пост: у канала с четырьмя живыми постами все четыре обновляются одним запросом.

### Расписание

Пост читается по затухающему графику от момента публикации — 15 минут, 30, час, 2, 4, 8, 24, 48 — и после этого не читается больше никогда. Момент опроса канала — самый ранний из графиков его живых постов; у канала, где живых постов нет, интервал берётся из его собственного темпа публикаций и зажимается в границы (по умолчанию от 30 минут до 12 часов).

Отсюда бюджет. По инвентарю на 500+ каналов это порядка 3–4 тысяч запросов в сутки — примерно один запрос в 20–25 секунд, то есть мягче, чем шёл backfill.

**Пропущенный замер пропадает, а не берётся позже.** Ноутбук закрыли на восемь часов — проснувшись, `watch` не будет догонять очередь: у каждого поста берётся тот замер, который соответствует его *текущему* возрасту, а пролетевшие просто не случились. Это не компромисс, а решение: замер, который должен был случиться на 30-й минуте жизни поста, а взят на восьмом часу — это не опоздавший замер ранней кривой, а другой замер под её именем. Цена — у постов, опубликованных ночью или во время простоя, ранней кривой не будет; они останутся измеримы по поздним сигналам.

По той же причине всё, что читает `message_metrics`, обязано брать возраст как `observed_at` минус дату публикации, а не как «какой это по счёту замер».

### Тихие часы

Ночью опрос не идёт: по умолчанию с 02:00 до 07:00 в зоне `watch_timezone`. Живые аккаунты спят, это снимает заметную долю суточных запросов, и ничего в этом корпусе не требует минутной реакции в четыре утра. Чтобы выключить — задать одинаковые `watch_quiet_from_hour` и `watch_quiet_to_hour`.

### Сессию держит один процесс

Это первый процесс в проекте, который живёт постоянно, и он занимает файл сессии на всё время работы. Два процесса на одном файле сессии — это испорченный файл и, в худшем случае, отозванная авторизация, поэтому теперь **каждая сетевая команда берёт эксклюзивную аренду**, а не берущая — отказывается:

```
$ uv run itgraph backfill --since 2026-05-01
the Telegram session itgraph.session is in use by itgraph watch pid=4131@olga-mini (since 2026-08-03 09:12).
One process at a time may hold it — two would corrupt the session file. Stop the running command (or the `itgraph watch` loop) and try again.
```

Практически: чтобы сделать `backfill`, `metadata`, `resolve` или `add`, цикл надо остановить. Аренда — это advisory-lock в Postgres, живущий на отдельном соединении, поэтому убитый процесс освобождает её сам: чистить нечего, PID-файлов нет.

`watch` останавливается по Ctrl-C или `SIGTERM`, дочитав текущий канал. Оговорка важная: обработчик сигнала выставляет флаг, который цикл читает **между** итерациями, — значит, цикл, заблокированный внутри одного `await`, по `SIGTERM` не остановится вообще. Именно поэтому у запросов есть срок, а у цикла — сторож (см. [обрыв связи](#что-происходит-при-обрыве-связи)); 90-секундный grace period пода — последняя линия, а не первая.

### Что происходит при лимитах

Короткий `FloodWait` пережидается и запрос повторяется — как везде. Длинный, на котором `backfill` останавливается с кодом 1, здесь **не останавливает цикл**: всё расписание сдвигается за конец ожидания, и работа продолжается. Пакетное задание может позволить себе выйти, а цикл — нет, потому что работать и есть его продукт.

Лимиты пишутся в `flood_events` под командой `watch`. Строка с `ResolveUsernameRequest` или `GetFullChannelRequest` под этой командой — это регрессия: цикл не имеет права тратить ни одного квотируемого запроса, peer он берёт из кэша сессии, как и `backfill`.

### Что происходит при обрыве связи

13 августа 2026 года цикл перестал собирать и не перестал работать: 67 часов `active (running)`, 551 канал просрочен, ни одной ошибки в логах после первой минуты. Telegram закрыл соединение, Telethon начал переподключение, цикл в этот момент отправил очередной запрос — а `send()` принимает запросы всё время, пока идёт переподключение. Запрос лёг в очередь отправки. Когда переподключение окончательно провалилось, Telethon завершил с ошибкой только те запросы, что уже ушли в сеть; тот, что остался в очереди, не был ни отправлен, ни завершён. `await` на нём не вернулся никогда.

Отсюда три вещи, каждая из которых закрывает свой слой:

- **У каждого запроса есть срок.** Прошёл — запрос бросается, а соединение считается негодным и закрывается: следующий канал не будет опрошен через то же соединение. Ожидание лимита при этом по-прежнему не ограничено, это разные вещи.
- **Цикл проверяет соединение перед каждым опросом** и переподключается сам. Пока связи нет, он не опрашивает никого и **не пишет никому ошибок**: обрыв — это не вина каналов, которые в этот момент были просрочены, и они не должны разъезжаться по backoff'у из-за него.
- **Цикл, который перестал продвигаться, выходит с ненулевым кодом**, и кластер поднимает его заново. Продвижение — это опрос, который чем-то закончился: сохранил, пропустил или получил ошибку от Telegram. Проверка живёт в отдельной задаче рядом с циклом, а не внутри него: проверка внутри срабатывает, только если цикл дошёл до своей следующей итерации, а он именно этого и не делал.

Простой запуск не тревожит: пустая очередь, тихие часы и сдвинутое лимитом расписание считаются нормальной работой, а не молчанием.

| настройка (`.env`) | что делает | по умолчанию |
|---|---|---|
| `watch_reconnect_delay_seconds` | пауза между попытками переподключиться | `30` |
| `watch_stall_minutes` | сколько цикл может не завершить ни одного опроса, прежде чем выйти | `30` |

### Посмотреть, что происходит

```bash
uv run itgraph watch-status
```

```
412 channel(s) scheduled, 7 due now
oldest overdue by 0:04:31
snapshots: 118 in the last hour, 2843 in the last day, 61204 in all
```

Команда не берёт аренду сессии — иначе её нельзя было бы запустить, пока цикл работает, то есть ровно тогда, когда она нужна.

### Чего `watch` не делает

Не строит рёбра, не считает никаких оценок, ничего никуда не отправляет и не трогает статусы каналов в инвентаре. Он складывает сырое; `itgraph derive` по-прежнему запускается отдельно и разбирает собранное так же, как и всё остальное.

Потолок `backfill_max_messages` на цикл не распространяется: он ограничивает, насколько глубоко в прошлое имеет смысл платить за обход, а не сбор вперёд. Канал, упёршийся в потолок, — один из самых активных в инвентаре, и слепое пятно именно на нём было бы худшим из возможных.

## Оповещения

Пока `watch` копит снимки, единственное, что уже можно посчитать без прогрева, — это **каскады репостов**: пост, который подхватили несколько независимых каналов.

```bash
uv run itgraph alerts    # найти каскады, записать оповещения
uv run itgraph bot       # доставлять их оператору
```

### Сколько это будет говорить

Примерно **одно оповещение в сутки**. Это не оценка, а замер по плотно собранным последним 30 и 60 дням, с исключением внутрисемейных репостов:

| семей подхватило пост | оповещений в сутки | что это |
|---|---|---|
| 1 | ~19 | «кто-то репостнул» — шум |
| 2 | ~1.1 | порог по умолчанию |
| 3 | ~0.35 | раз в три дня |
| ≥4 | ~0 | один случай за два месяца |

Между шумом и молчанием почти нет промежутка, поэтому пороги — `(2, 3)` и на этом заканчиваются: четвёртый не срабатывал бы никогда и вводил бы в заблуждение того, кто следующим откроет конфиг.

**Это ожидаемо, а не поломка.** Объём принесёт следующий change со скорингом метрик; доставка сделана раньше именно для того, чтобы к моменту объёма дедуп, потолки и формат сообщений были уже проверены на маленьком потоке.

Медиана до второй семьи — 4 часа 37 минут. Каскад складывается часами, поэтому оповещение никогда не про «минуту назад»; в сообщении явно написано, сколько посту времени.

### Виральность: пост, который идёт лучше обычного

Второй источник оповещений — не «кого репостнули», а «сколько собрал». Считается по снимкам, которые копит `watch`:

```bash
uv run itgraph baselines   # пересчитать, что для канала нормально
uv run itgraph score       # найти всплески, записать оповещения
```

**`baselines` обязателен перед первым `score`.** Без него сравнивать не с чем, и проход честно ничего не делает и говорит об этом вслух — вместо того чтобы подставить какие-нибудь значения по умолчанию. Дальше — **каждый день** (CronJob `itgraph-baselines`, 04:30 по Москве): опора канала — это его собственные последние посты, и она свежа ровно настолько, насколько свеж последний пересчёт.

Оценка — z-score, и читается она так: **z 3 значит «примерно втрое больше того, что пост такого возраста на этом канале обычно набирает»**. Не «втрое больше среднего по каналу»: возраст поста учтён отдельно, поэтому пост в 15 минут и пост в 8 часов сравниваются каждый со своей нормой.

```
  ожидаемое(возраст) = опора канала × фактор × кривая(возраст, тип, метрика)
  z                  = log(факт / ожидаемое) / разброс
```

**Опора канала — его собственные последние посты.** Медиана того, что набрали к восьми часам его 20 последних постов (`baseline_recent_posts`) не старше 90 дней, при минимуме в 10. Фактор для неё равен единице: это уже значение в восемь часов. Считается по последним постам, а не по окну в днях, потому что так опора успевает за быстро растущим каналом. Пост, чей восьмой час пришёлся на тихие часы сборщика (публикации около 19:00), в опору не попадает: его восьмичасового значения никто не видел.

Раньше опорой была медиана «зрелых» постов (28–120 дней) с фактором типа канала — и она **с июля не двигалась**: сырой слой хранит первое чтение, а `watch` читает каждый пост в нулевом возрасте, так что ни один пост после бэкфилла в неё не попадал. 72 канала из 229 сидели больше чем на 1 z от нуля: выросшие оповещали почти на каждом посте, а каналы, чьи посты набирают неделями, не могли оповестить никогда. С собственной опорой таких каналов 3. Зрелая медиана осталась **запасной** — для каналов, которым не хватает свежих постов; их проход и пересчёт считают отдельно («scored against their settled history»), а за две недели от них пришло 2 оповещения из 196.

Порог по умолчанию — **z 3.7, около восьми сообщений в сутки** после свёртки серий. Один порог на все метрики: деление на собственный разброс метрики — это ровно то, что делает z сравнимым между ними, и отдельная настройка на каждую всё это обнулила бы.

Порог переоценивали дважды, и это стоит знать, если сравниваете с более старыми записями. Он начинался с 3.0; исправление опоры — ограниченное окно медианы и разброс по возрастным полосам — сдвинуло саму шкалу, и 3.0 стал давать в полтора раза больше. 3.3 воспроизводил прежний объём на той же неделе. Потом собственная опора убрала из разброса сдвиги каналов — он сузился с 0.40 до 0.18 у личных каналов, с 0.23 до 0.18 у агрегаторов, — и тот же пост стал набирать больший z; 3.7 воспроизводит прежние восемь сообщений в сутки на тех же двух неделях. Порядок оба раза: чинить, померить, потом переоценивать — иначе не сказать, что на что повлияло.

Один пост даёт **одно оповещение** — по той метрике, которая набрала больше всех. Иначе самый интересный пост дня прислал бы четыре сообщения в течение часа.

**Одно событие канала — одно сообщение.** Когда аудитория вырастает у всего канала разом (реклама, трансляция, накрутка), порог переходят сразу все его свежие посты. По отдельности каждый оценён верно, но это одно событие, а не семь. Поэтому первый всплеск канала становится *головным*, а все всплески того же канала в течение `alert_spike_fold_hours` (6 ч) от него **сворачиваются** в него: отдельно они не отправляются, а в головном сообщении написано «вместе с ним выше нормы ещё N пост(ов) канала». До этого 41% оповещений о всплесках приходили такими сериями; у `@aigency360`, которому каждый вечер одинаково накручивают все посты дня, было 66 сообщений за две недели, стало 10.

Свёрнутое оповещение не выбрасывается: оно лежит в очереди со ссылкой на головное (`folded_into`), поэтому пост не поднимется заново, когда окно закроется, а `--replay` и `/status` его видят. Свёртка, пришедшая уже после отправки головного, ничего не присылает: о событии уже сказано.

Окно отсчитывается от головного и не скользит: шесть часов накрывают самый широкий разрыв внутри одного события (5.5 ч), а всё, что через 12–24 часа, — уже другое событие. Сутки свернули бы во вчерашнее оповещение и совсем другие посты.

**Пачка сообщений — один пост.** Сообщения одного канала, опубликованные меньше чем через `scoring_burst_seconds` (60 с) друг за другом, оцениваются как один пост — по первому сообщению, как альбом по первой части. Так публикуют «текст, а потом каждое видео отдельно», и альбомом Telegram это не считает.

**Собственный разброс возрастной полосы — только от 100 разных постов** (`baseline_min_band_spread_posts`); иначе полоса делится на общий разброс метрики. Двадцать чтений могут оказаться четырьмя постами, а разброс по нескольким постам занижен — то есть завышает z. 18 октября так у полосы 150 минут типа `event` вышло 0.104 вместо 0.345, и пост с ×1.4 от нормы получил z 6.86.

**Комментарии оцениваются как счётчик**, а не логарифмом отношения: больше половины их чтений — ровно ноль, и логарифм такой счётчик описать не может (при пороге 3.7 он давал 0,1 сообщения в день). Ожидание — среднее восьмичасовых значений 20 свежих постов канала вместе с нулями, умноженное на кривую, посчитанную как отношение сумм (нули тоже в ней). Счётчик считается отрицательно-биномиальным с этим средним и рассеянием, которое подбирается для вида канала по максимуму правдоподобия и хранится в запуске базовых линий (`metric_baselines.dispersion`). Оценка — z с тем же правым хвостом, поэтому порог тот же, `alert_spike_z`, и пост по-прежнему получает одно оповещение — по самой сильной метрике.

Запасной линии по зрелой истории у комментариев нет: у канала, которому не хватает свежих постов, комментарии не оцениваются. Меньше `alert_spike_comments_min` (10) комментариев не оповещает, как бы невероятно это ни было для канала. Оповещение называет число и обычное для канала на этом возрасте: «💬 Комментарии — 117, обычно меньше одного (z 14.2)». Запуск базовых линий без рассеяния — снятый до этой версии — комментарии не оценивает, и итоговая строка прохода так и говорит; их начнёт оценивать ближайший `itgraph baselines`.

Повтор на этом коде за 16 дней до 7 ноября 2026, с базовыми линиями, обновлёнными на каждый день: 0,75 сообщения в день по комментариям; из двадцати самых сильных за 30 дней семнадцать — естественная реакция на новости. Подробности и отвергнутые модели — в `docs/PLAN.md`.

Каналов без базовой линии проход не молчит, а считает. Базовая линия есть у канала, у которого хватает либо свежих постов, либо зрелой истории в окне 28–120 дней; каналы, которые публикуют слишком редко и для того, и для другого, остаются без линии. Окно зрелой медианы ограничено сверху сознательно: без верхней границы медиана считалась по всей истории канала (медианному посту в ней — полгода, самому старому — восемь лет), и выросший канал сравнивался с собой прежним.

«От этого канала не было оповещений», «этот канал не оценивается» и «этот канал оценивается по старой истории» — три разных факта, и в итоговой строке они различимы.

### Подобрать порог, не дожидаясь суток

```bash
uv run itgraph score --replay                    # что бы сработало за неделю
uv run itgraph score --replay --threshold 2.5    # то же при другом пороге
uv run itgraph score --replay --since 3          # за трое суток
```

`--replay` ничего не пишет и никому не отправляет: он печатает список постов, которые сработали бы, с z, фактическим и ожидаемым значением и возрастом; у свёрнутого — в какой головной он свёрнут. Это тот же самый проход, которому передан момент в прошлом, а не вторая реализация — иначе она сходилась бы с боевой на всех случаях, которые кто-нибудь проверил, и расходилась на том единственном, который важен.

### Свежесть данных

Оповещения настолько свежи, насколько свеж `itgraph derive`. Полный проход занимает около 11 секунд и сети не касается, поэтому ответ — расписание, а не инкрементальность:

```bash
uv run itgraph derive && uv run itgraph alerts
```

Проход сам печатает, насколько стары рёбра, которые он читал. Это не украшение: нормальное состояние системы оповещений — молчание, и без этой строки «ничего не разлеталось» и «derive не запускался с вторника» выглядят одинаково.

### Роль в базе для бота

Токен бота — единственный секрет проекта, который реально может оказаться на чужой машине. Поэтому у бота своя роль, которая пишет только состояние доставки двух очередей оповещений: он ничего не может записать ни в инвентарь, ни в сырой слой, ни в снимки, ни в рёбра, ни в данные YouTube, а в очереди YouTube не может ни поднять оповещение, ни поменять, о каком видео оно и с какой оценкой.

Миграция создаёт роль **без пароля** — пароль в файле миграции был бы закоммиченным секретом. Пароль задаётся руками, один раз:

```sql
ALTER ROLE itgraph_bot LOGIN PASSWORD 'сгенерируйте-длинный';
```

и боту даётся отдельный DSN — **через `BOT_DATABASE_URL`, а не подменой `DATABASE_URL`**:

```
DATABASE_URL=postgresql+asyncpg://itgraph:...@localhost:5433/itgraph
BOT_DATABASE_URL=postgresql+asyncpg://itgraph_bot:...@localhost:5433/itgraph
```

Разница не косметическая. Коллектор читает настройки один раз при старте, поэтому `.env`, переведённый на роль бота, продолжает работать до первого перезапуска — а потом `watch`, `derive`, `backfill` и `mark` отказывают все сразу, потому что этой роли запрещена любая запись в таблицы сбора. Две отдельные переменные так спутать нельзя: каждый процесс читает свою.

Если `BOT_DATABASE_URL` не задан, бот работает под общими правами — это поддерживаемое состояние, и он печатает при старте, под какой ролью подключился, чтобы незащищённый вариант был виден, а не подразумевался. Остаточный риск назван честно: роль ограничивает запись, но не чтение — бот читает тексты постов, названия каналов и, для оповещений YouTube, данные API из `yt_raw_*`, — поэтому пока нет причины выносить его наружу, пусть живёт на той же машине.

### Метрики для общего мониторинга

`itgraph metrics` отдаёт серии на порту 9090, `GET /metrics`. Это отдельный процесс, поэтому ни коллектор, ни бот портов не открывают. Каждая серия считается в момент запроса из того, что уже записано в базе, поэтому остановившийся коллектор измеряется так же, как работающий. Порт отвечает только на этот один запрос, запрос ничего не меняет, в Telegram, YouTube и B2 процесс не ходит. Если база не отвечает, ответ 503.

| Серия | Что значит |
|---|---|
| `itgraph_telegram_last_poll_timestamp_seconds` | когда коллектор последний раз закончил опрос канала |
| `itgraph_telegram_oldest_overdue_seconds` | насколько опаздывает самый старый канал в очереди опроса |
| `itgraph_telegram_failing_channels` | у скольких каналов последний опрос не удался |
| `itgraph_telegram_quiet_hours` | 1 в тихие часы коллектора, когда он ничего не опрашивает |
| `itgraph_telegram_last_flood_timestamp_seconds` | когда записан последний лимит |
| `itgraph_youtube_quota_spent_units{pool}` | сколько единиц пул забронировал за этот квотный день |
| `itgraph_youtube_quota_cap_units{pool}` | потолок пула на квотный день |
| `itgraph_youtube_quota_exhausted{bucket}` | 1, если YouTube объявил день этой квоты законченным |
| `itgraph_youtube_last_complete_pass_timestamp_seconds` | когда последний раз завершился проход `yt watch` |
| `itgraph_youtube_oldest_payload_age_seconds{kind}` | возраст самых старых данных API каждого вида; серии нет, если данных этого вида нет |
| `itgraph_alerts_oldest_undelivered_seconds{platform}` | сколько ждёт самое старое недоставленное оповещение очереди `telegram` или `youtube`, удержанные до дайджеста тоже |
| `itgraph_alerts_failing{platform}` | сколько недоставленных оповещений очереди набрали порог неудачных попыток |
| `itgraph_baselines_completed_timestamp_seconds{platform}` | когда завершился последний пересчёт базовых линий платформы; 0, если его не было |
| `itgraph_baselines_channels{platform,state}` | сколько каналов в этом пересчёте в охвате (`in_scope`) и сколько получили базовую линию (`with_baseline`) |
| `itgraph_youtube_weekly_list_computed_timestamp_seconds{route}` | когда посчитан последний список недели этого языка; 0, если его не было |
| `itgraph_youtube_weekly_list_delivered_timestamp_seconds{route}` | когда ушёл последний доставленный список недели этого языка; 0, если такого не было |

Процесс подключается под ролью `itgraph_metrics`. Её создаёт миграция без пароля и даёт ей чтение только служебных таблиц, из таблиц `yt_raw_*` только столбец с моментом получения, из `yt_alerts` только моменты и состояние доставки, из пересчётов базовых линий обеих платформ только момент завершения и число каналов, а из списков недели только язык и моменты: прочитать название, handle или описание, узнать, о каком видео оповещение и с какой оценкой, увидеть опору канала, кривую или фактор эта роль не может, писать не может никуда. Исключённое по языку оповещение YouTube не считается ни недоставленным, ни застрявшим: его и не должны были отправлять. Значения меток берутся только из констант и перечислений кода, поэтому канал, видео или человек в хранилище метрик попасть не могут. Правила и дашборд лежат в инфраструктурном репозитории; оповещения проекта в его чате к ним отношения не имеют.

### Роль для чтения базы

`itgraph_reader` — роль для оператора, который смотрит базу через туннель (`deploy/runbook.md`, «База через туннель»). Ни один процесс проекта под ней не подключается. Она читает все таблицы и представления схемы `public`, включая `yt_raw_*` и заметки оператора, и ничего не может изменить: у неё нет прав на `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, на последовательности и на создание таблиц. Таблицу, которую создаст следующая миграция, роль читает сразу: права по умолчанию выданы роли, которая выполняет миграции.

Миграция создаёт её без пароля и без права входа. Пароль задаёт деплой из `itgraph_reader_postgres_password`; если вход пуст, роль снова не может войти. Когда деплой меняет или убирает пароль, он завершает открытые сессии роли.

Сессия роли начинается с ограничений: транзакции только для чтения, `work_mem` 16 МБ, запрос не дольше 10 минут, открытая транзакция без дела не дольше 5 минут, не больше 4 подключений сразу. Это защита от случайностей, а не граница: сессия может снять любую настройку, кроме лимита подключений. Граница — права: даже в сессии, снявшей режим только для чтения, запись отклоняется с `permission denied`.

### Что бот делает и чего не делает

Отправляет оповещения туда, куда настроено, и **не отвечает никому другому**: сообщение из чата, которого нет в настройках, отбрасывается до того, как отработает хоть один обработчик. Имя бота видно всем, а инвентарь — это ваши подписки.

Куда — это **назначение**: чат, и в нём топик или нет. Оповещения Telegram идут в чат `alert_chat_id`, как всегда. Оповещения YouTube — в отдельный чат-форум `youtube_alert_chat_id`, в топик языка канала: `youtube_alert_topic_en` или `youtube_alert_topic_ru`. Язык читается **в момент отправки**: если канал переразметили, пока оповещение ждало, оно уходит в топик нового языка. Каналы с языком `other` оповещений не получают: такое оповещение закрывается как исключённое, ничего не отправляя, и `/status` считает его отдельно. Канал, который перестал быть сидом, своё уже поднятое оповещение всё равно получает. Пока чат YouTube не задан, оповещения YouTube не отправляются и копятся как недоставленные.

Кнопок под оповещениями нет. Они собирали оценку 👍/👎 с первого дня, и за три месяца ею воспользовались один раз — для проверки; порог обсуждали, перечитывая оповещения, а не по кнопкам. Под старыми сообщениями кнопки остались: на нажатие бот отвечает «отзывы больше не собираются» и снимает их с этого сообщения, ничего не записывая.

У каждого назначения **свой учёт**: свой суточный потолок, свои тихие часы и своя сводка. Всплеск в Telegram не тратит потолок YouTube, а английский топик — русский. Значения общие для платформы: у Telegram `alert_daily_cap` (20), `alert_quiet_*_hour`, `alert_digest_hour`, у обоих топиков YouTube — `youtube_alert_daily_cap` (10), `youtube_alert_quiet_*_hour`, `youtube_alert_digest_hour`, `youtube_alert_timezone`.

Ночью бот молчит (по умолчанию 02:00–07:00) и в 09:00 присылает сводку тем, что накопилось, — с указанием, сколько там всего. Поднятое в тихие часы и сверх потолка **помечается как удержанное до сводки** и больше не попадает в то, что бот забирает для прямой отправки: раньше десять таких в голове очереди останавливали всю прямую доставку до утренней сводки. Удержанное уходит именно в сводке, даже если потолок к тому времени освободился. Сводка, которая не помещается в одно сообщение Telegram (4096 символов), уходит **частями**: каждое оповещение целиком в одной части, в первой — сколько их всего. Неудачная часть засчитывается неудачной попыткой каждому своему оповещению и отправляется снова на следующем проходе; уже отправленные части не повторяются. Раньше такая сводка падала целиком и повторялась каждую минуту. Час сводки обязан быть вне тихого окна, и настройки это проверяют при загрузке.

Всё, что взято из поста, канала или видео, в сообщении экранируется: сообщения в HTML, и `<` или `&` в тексте Telegram отверг бы при каждой попытке.

`/status` отвечает о платформе того чата, где его спросили, и в тот же топик. В чате Telegram — сколько оповещений поднято (и сколько из них свёрнуто в серии), сколько не доставлено и сколько из них ждут сводки, сколько застряло и насколько отстаёт очередь опроса. В чате YouTube — сколько оповещений YouTube поднято, свёрнуто и исключено по языку, по каждому топику — сколько не доставлено, ждут сводки и застряло, когда последний раз полностью прошёл `yt watch`.

При старте бот спрашивает у Telegram каждый настроенный чат и **не запускается**, назвав настройку, если чата не знает или если чат с топиками — не форум. Проверить, что топик существует, Bot API без отправки не даёт: недоступный топик даёт неудачную отправку, она копится в попытках и в `itgraph_alerts_failing{platform="youtube"}`, и в другое место оповещение не уходит.

### Чаты и топики

`alert_chat_id` — это **ваш** Telegram-id (или id группы), а не id бота. Узнать: напишите боту что-нибудь и посмотрите

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | grep -o '"chat":{"id":[-0-9]*'
```

Бот не может написать человеку первым — пока вы не нажмёте Start, отправка падает с «bot can't initiate conversation with a user». Оповещение при этом не теряется: оно остаётся недоставленным и уйдёт со следующей попытки.

**Чтобы оповещения видели несколько человек, кода менять не нужно:** заведите группу, добавьте туда бота и поставьте id группы (он отрицательный, у супергрупп начинается с `-100`). **В BotFather выключите privacy mode** либо обращайтесь к боту явно — `/status@имя_бота`. С включённым privacy бот получает только адресованные ему команды.

**Чат YouTube** — супергруппа с включёнными топиками и двумя топиками, английским и русским. Топики создаёте вы; бот в чате обычный участник, не администратор, и создавать или закрывать топики не может — так утёкший токен не может их переименовать, закрыть или удалить. Id топика берётся из ссылки на любое сообщение в нём: «Копировать ссылку» даёт `https://t.me/c/<id>/<топик>/<сообщение>`, id чата — это `-100<id>`. Чат и оба топика задаются вместе или не задаются вовсе: половину настройки бот откажется загрузить.

Публичный канал — это уже другой продукт, а не смена одного числа: `/status` отдаёт операционную изнанку и публиковаться не должен.

Бот не берёт аренду сессии и не открывает MTProto, поэтому спокойно работает одновременно с `itgraph watch`.

## Граф: репосты и упоминания

Сырой слой хранит сообщения целиком, но ничего в них не разбирает. `derive` строит из этих строк рёбра графа — кто кого репостит и упоминает, — а `resolve` добирает username и название каналам, найденным по ссылке. Это две разные команды, потому что операционно у них нет ничего общего: `derive` быстрый, повторяемый и **в сеть не ходит вообще**; `resolve` медленный, лимитируемый и несёт тот же риск для аккаунта, что и весь сетевой код проекта.

```bash
uv run itgraph derive     # построить рёбра из сырого слоя
uv run itgraph resolve    # дорезолвить найденные каналы (идёт в сеть)
uv run itgraph derive     # второй проход дописывает рёбра упоминаний
```

### Почему два прохода, а не один

Форвард несёт числовой id — это первичный ключ канала, поэтому и строку канала, и ребро можно создать сразу, в том же проходе. Упоминание несёт только `@username`: без id ни строки, ни ребра не создать. Такие username складываются в отдельную очередь (`pending_mentions`); `resolve` превращает их в каналы, и **следующий** `derive` дописывает рёбра. Рёбра упоминаний по построению отстают на один цикл, и граф достраивается за два-три чередующихся прохода: derive → resolve → derive. Это задумано так, а не ограничение, которое надо обходить.

`derive` **безопасно перезапускать в любой момент**: проход по неизменившимся данным не пишет ничего (рёбра вставляются с `ON CONFLICT DO NOTHING` по естественному ключу `источник + сообщение + тип + канал-цель + пост-цель`). Производные данные одноразовы — их всегда можно перестроить из сырого слоя, и именно поэтому эту часть дёшево ошибиться и дёшево итерировать, в отличие от сбора.

> **После миграции «post level forwards» таблица `edges` пуста — нужен один прогон `derive`.** Миграция добавляет в рёбра ссылку на исходный пост, а вставка идёт с `ON CONFLICT DO NOTHING`: дописать новые колонки в уже существующие строки такой вставкой нельзя — повторный `derive` посчитал бы их за конфликт и оставил колонки пустыми, отчитавшись об успехе. Поэтому миграция очищает `edges` целиком, и после `alembic upgrade head` граф восстанавливается одним `derive`. Сырой слой не трогается, перекачивать ничего не нужно; `pending_mentions` тоже остаётся на месте.

### derive

| опция | что делает |
|---|---|
| `--rebuild` | очистить `edges`, `pending_mentions` и источники упоминаний и построить заново. Единственный путь, удаляющий производные данные; `channels` и сырой слой он не трогает, поэтому канал, найденный форвардом, переживает `--rebuild`, а его рёбра просто перестраиваются |
| `--batch-size` | сообщений за партию (по умолчанию 1000) |

Что попадает в граф:

- **форвард из канала** → ребро `forward` к каналу-источнику. Ребро несёт и сам исходный пост: его id и дату первой публикации (`fwd_from.channel_post` и `fwd_from.date`). Форвард, не называющий исходного поста, всё равно даёт ребро — эти поля просто остаются пустыми. Форвард от пользователя, со скрытым источником (приватность автора) и репост канала самого себя — не рёбра: на том конце нет второго канала.
- **`@username` и ссылка `t.me/...`** → ребро `mention`. Ссылка на один пост (`t.me/name/123`, `t.me/c/<id>/<msg>`) несёт id этого поста; ссылка на канал целиком и обычное `@упоминание` — нет. Ссылка-приглашение (`t.me/joinchat/...`, `t.me/+...`), служебная ссылка — та, где первый сегмент пути `t.me` занимает под действие, а не под канал (`t.me/addlist/...` и `t.me/addlist?slug=...` — папка каналов, `t.me/addstickers/...` — набор стикеров, а также `addemoji`, `addtheme`, `setlanguage`, `share`, `proxy`, `socks`, `login`, `confirmphone`, `invoice`, `giftcode`, `contact`, `boost`), упоминание бота или человека, ссылка не на Telegram — не рёбра. Служебное слово выглядит как обычный юзернейм, поэтому без явного списка каждая такая ссылка заводила в `pending_mentions` несуществующий канал `addlist` или `addstickers`, который разрешиться не мог.
- одно сообщение, сославшееся на **один и тот же пост** дважды, даёт одно ребро; но две ссылки на разные посты одного канала — это два ребра, а форвард из канала и его же упоминание в том же сообщении — два ребра разных типов.
- **пересланный альбом** приходит несколькими сообщениями, у каждого свой `fwd_from`. Каждое даёт своё ребро, и все они несут общий id группы (`grouped_id`); derive их не схлопывает — свести альбом в одно событие это решение подсчёта, а оно относится к анализу, а не к разбору. `grouped_id` осмыслен только вместе с каналом-источником.

**Источники и цели.** Рёбра строятся только из каналов в статусе `candidate`, `seed` или `maybe`. Статусы перечислены явно, а не как «всё, кроме `rejected`»: когда в `channel_status` появится новое значение, его придётся включить или исключить осознанно — белый список уронит новый статус заметно (рёбра пропадут на следующем `--rebuild`), чёрный впустил бы его молча, а для таблицы, растящей инвентарь, шумный отказ безопаснее. Каналы-обсуждения (`is_chat`) источниками не служат, даже если их статус в списке: форвард внутри комментария — это репост человека, а не публикация чата. Каналы-**цели** не фильтруются: ребро к отклонённому каналу всё равно пишется — то, что сид репостит отклонённый канал, это факт о сиде.

**Отклонение вступает в силу только на `--rebuild`.** Обычный `derive` ничего не удаляет, поэтому рёбра канала, отклонённого уже после сбора, остаются на месте до следующего `derive --rebuild`, который очищает `edges` и строит их заново — уже без отклонённого источника. Сам инвентарь при этом не трогается: каналы, которые такой источник ввёл раньше (форвардом или упоминанием), остаются в `channels` со своим исходным `discovered_via`. Каналы вообще никогда не удаляются — `--rebuild` перестаёт добавлять новое, а не отменяет прошлое.

Время в пути — разница между датой исходного поста и датой репоста — намеренно не хранится: это вычитание двух колонок одной строки, и держать его в таблице наблюдений значило бы завести там первую производную величину. По той же причине альбом не схлопывается и никакие счётчики в рёбра не пишутся.

Персональные данные в граф не попадают, и в сыром слое их нет: id пользователей и подписи коллектор убирает до записи, а деривация читает только каналы. Именно это оставляет производные таблицы безопасными для визуализации.

### resolve

Резолвит две очереди сразу: каналы, найденные форвардом (по id), и username из очереди упоминаний (публичным поиском). Подчиняется тем же правилам, что и `backfill`: последовательные запросы, случайная пауза между ними из той же полосы, честное ожидание короткого `FloodWaitError` — и та же остановка на длинном, с тем же кодом возврата 1 и тем же лечением (дождаться и запустить снова). Останавливаются при этом обе очереди сразу: лимит относится к аккаунту, а не к той ссылке, которая оказалась следующей.

| аргумент / опция | что делает |
|---|---|
| `TG_ID` | резолвить ровно этот канал и больше ничего |
| `--limit` | не больше стольких запросов за запуск, суммарно по обеим очередям |
| `--delay` | опорная пауза между запросами, секунды |
| `--retry-failed` | повторить и те ссылки, что не резолвились в прошлый раз |
| `--min-sources` | резолвить только username-ы, упомянутые как минимум стольким числом разных каналов |

### Один канал по id

Очередь по id обходится в порядке `tg_id`, поэтому `--limit 1` резолвит **наименьший** id из ожидающих, а не тот, о котором вопрос. Чтобы спросить про один конкретный канал, он называется прямо:

```bash
uv run itgraph resolve 2000000001                  # один запрос, и только он
uv run itgraph resolve 2000000001 --retry-failed   # он же, после прошлой неудачи
```

Очередь упоминаний при этом не трогается вообще — ни запроса, ни чтения. `--limit` и `--min-sources` вместе с `TG_ID` команда не принимает: первый ограничивает прогон, который и так в один запрос, второй сортирует очередь, которая не разбирается.

**Аргумент сужает очередь, а не заменяет её правила.** Названный канал должен в этой очереди быть, иначе команда откажется — и скажет, чем именно:

| состояние | что делать |
|---|---|
| такого канала в инвентаре нет | `itgraph add`, или проверить id |
| уже отрезолвлен | ничего, username и название на месте |
| падал в прошлый раз | повторить с `--retry-failed` |

Отказ происходит **до подключения к Telegram**: аренда сессии не берётся, так что несуществующий id не может оказаться причиной, по которой не стартует `itgraph watch`.

Id берётся в том виде, в каком его хранит инвентарь, — как печатает `itgraph list`, без префикса `-100`, которым его показывают некоторые клиенты.

### Очередь упоминаний идёт по весу свидетельства

Очередь по id дешёвая, а очередь упоминаний — нет: каждая строка это один `contacts.resolveUsername`, которых пара сотен в сутки и которые не батчатся. Поэтому важно не сколько их, а в каком порядке.

Замер на реальной очереди: **девять из десяти username-ов упомянуты ровно одним каналом**. В графе «кто кого репостит и упоминает» они дают вершины со степенью 1 — то есть суточная квота уходила на самое неинформативное, что в инвентаре бывает.

```
2888 строк в pending_mentions
├─  365  username уже существует как канал  → в очередь не попадают вовсе
├─  122  падали в прошлые запуски           → только под --retry-failed
└─ 2401  собственно очередь
     ├─ 2152  упомянуты одним каналом
     └─  248  упомянуты двумя и больше       ← голова, ~день квоты
```

Поэтому очередь сортируется по числу **разных** каналов, упомянувших username, по убыванию; `first_seen_at` остался тай-брейком, так что внутри одного захода `--limit` детерминирован. Повторное упоминание внутри одного канала — это по-прежнему одно мнение одного канала, а не два.

```bash
uv run itgraph resolve --limit 200 --min-sources 2   # голова очереди, два дня
uv run itgraph resolve --limit 200                   # дальше хвост, тем же порядком
```

Между заходами порядок может сдвинуться: новый `derive` добавит источник и поднимет username выше других. Это задумано — новое свидетельство должно перерасставлять приоритеты, — но означает, что очередь упоминаний даёт более слабое обещание, чем очередь по id, которая обходит одни и те же строки в одном и том же порядке всегда.

**Username, у которого канал уже есть, не запрашивается вообще.** Такие строки копятся из-за асимметрии двух очередей: канал, найденный форвардом и отрезолвленный по id, получает username, но строку в `pending_mentions`, ждавшую то же имя, никто не убирал — удалением занималась только очередь упоминаний. Запрос по такой строке может вернуть лишь канал, который в инвентаре уже есть. Теперь очередь их пропускает, а резолв по id удаляет строку, которую сам же сделал лишней. Накопившиеся уходят на ближайшем `derive --rebuild`.

**Кем упомянут username, записывает `derive`**, парами «канал → username», а не счётчиком: счётчик сломал бы главное свойство деривации — повторный проход по неизменившимся данным ничего не пишет, а инкремент пишет всегда. Пары складываются с `ON CONFLICT DO NOTHING` и сколько бы раз проход ни повторился, счёт не поедет. Источники удаляются вместе с username-ом, когда тот резолвится, и вместе с очередью на `derive --rebuild`.

> **После миграции таблица источников пуста, пока не прогнан `derive`.** До этого у всех username-ов ноль источников, `--min-sources 2` вернёт пусто, а обычный `resolve` тихо откатится к порядку поступления. Заполнить в миграции нельзя: счётчики берутся из разбора payload'ов, а замораживать копию парсера внутри alembic-ревизии — плохая идея. Поэтому `resolve` это замечает и предупреждает в логе. Лечится одним обычным `itgraph derive` — без сети, без `--rebuild`.

**`resolve` — единственная команда, которая тратит `contacts.resolveUsername`.** Ни `backfill`, ни `metadata` его больше не трогают, так что суточную квоту на резолв расходует только она — и планировать её можно, не оглядываясь на остальные. Это самая жёсткая квота в проекте: батч-формы у метода нет, поэтому очередь упоминаний разбирается со скоростью примерно пары сотен в сутки, и ускорить её нечем. Растянуть по дням через `--limit` — единственный рычаг.

Резолв канала по id требует `access_hash` — он выдаётся на каждый аккаунт свой и в сыром payload не хранится; Telethon кэширует его в файле сессии по мере сбора. Поэтому нерезолвящийся id — это промах кэша, а не приговор: следующий `backfill`, наткнувшись на тот же канал, может сделать его резолвящимся. Обычный запуск пропускает ранее упавшие ссылки, а `--retry-failed` пробует их снова — считать первую неудачу окончательной значило бы молча обрезать граф. Резолв username хэша не требует (это публичный поиск), поэтому у упоминаний этой проблемы нет — но именно они и стоят квоты.

То, что оказалось пользователем или ботом, а не каналом, канала не создаёт и записывается как таковое: граф хранит только каналы.

## Аффилированные каналы

Авторы держат по несколько своих каналов и активно репостят себя же. Каждый такой репост — реальное наблюдение и настоящее ребро, но это не связь между двумя людьми: по числу рёбер такой канал ложно выходит в топ «кто репостит разных». Чтобы метрики ролей могли эти рёбра вычесть, каналы одного автора нужно связать.

```bash
uv run itgraph affiliates                          # предложить пары, ранжировать
uv run itgraph family @main @podcast               # подтвердить пару
uv run itgraph family @a @b @c @d                  # подтвердить сразу группу
uv run itgraph family @main @other --reject        # отклонить
uv run itgraph channels --family @podcast          # посмотреть семью
```

`affiliates` **не ходит в сеть**: всё, что ему нужно, уже собрано — инвентарь, рёбра и описания каналов из `itgraph metadata`. Поэтому пороги можно перебирать сколько угодно, повторный запуск ничего не стоит.

Показываются только пары, где **хотя бы один канал в статусе `seed`**. Остальные считаются и сохраняются как обычно — их показывает `--any-status`, — просто ревьюить пару из двух каналов, ни один из которых ещё не в скоупе, значит отвечать на вопрос, которого пока никто не задал. Как только один из них принят, пара появляется в списке сама, ничего пересчитывать не надо.

Фильтр не стоит четырём сигналам из пяти ничего, и это структурно: рёбра есть только у каналов, которые обошёл `backfill`, а он ходит по сидам; описания — только у тех, что забрал `metadata`, и он тоже по сидам. Так что у концентрации, взаимной плотности, ссылок в описании и подписанного хендла сид с одной стороны есть всегда. На реальной базе все 72 скрытые пары пришли от одного токенного сигнала, причём 24 из них называют уже отклонённый канал.

### Команда предлагает, решаете вы

`affiliates` никогда не пишет связь. Он считает сигналы, складывает их в ранжированный список и сохраняет вместе с каждой парой то, на чём предложение основано. Записывает семью только `itgraph family` — вручную.

Порядок подтверждения не важен, и не важно, какие именно пары нашёл детект: пара, соединяющая две семьи, их сливает. Если группа известна целиком, её можно назвать одной командой — записываются все пары между перечисленными каналами.

Это не осторожность ради осторожности: на этих данных **нет порога, который отделяет второй канал автора от близкого коллеги**. Ошибочно подтверждённая семья вычтет из метрик настоящие межавторские рёбра, то есть испортит ровно то, что чинит.

Отклонение тоже сохраняется — именно затем, чтобы пара не предлагалась на каждом следующем запуске. Оно берёт ровно два канала: это утверждение про пару. И означает оно «эта пара не свидетельство», а не «эти двое не родня» — если каналы связаны другими подтверждениями, они остаются одной семьёй.

`--withdraw` отменяет любое решение и тоже берёт два канала. Отозванная пара разрывает семью, только если больше ничто не связывало две её части; если связывало — семья не меняется.

### Пять сигналов

| Сигнал | Что значит | Порог |
|---|---|---|
| ссылка в описании | описание одного канала называет другой | — |
| подписанный хендл | канал называет в своём описании `@хендл`, который несут его же и соседние username | `--min-token-length`, `--max-handle-token-channels` |
| общий токен в username | `gonzo_reviews` ↔ `gonzo_podcast` | `--min-token-length`, `--max-token-channels` |
| концентрация исходящих | доля рёбер канала, уходящая в одного адресата | `--min-out-edges`, `--max-share` |
| взаимная плотность | A и B репостят друг друга помногу | `--min-mutual-edges` |

Два замера по реальной базе (504 сида, 15 651 ребро, 195 описаний) определили дизайн больше, чем исходная интуиция:

**Взаимность в описаниях требовать нельзя.** Взаимных ссылок ровно одна пара. Из 37 односторонних 31 ведёт в канал, у которого описания нет вообще, — обратную ссылку негде искать. Требование взаимности мерило бы покрытие метаданных, а не аффилированность, поэтому односторонняя ссылка идёт как самостоятельное свидетельство и за непроверяемую обратную не штрафуется. Кстати, в описаниях доминируют `@упоминания`, а не `t.me`-ссылки: 155 против 34.

**У токена важна редкость, а не длина.** Без ограничения на частоту сигнал даёт 216 пар, и почти все — от слов вроде `channel`, `tech`, `news`, `jobs`, `data`, каждое на 5–11 несвязанных каналах. Это тема, а не автор. `--max-token-channels 3` оставляет 44 пары.

**Сигналы друг друга не подтверждают.** Взаимное описание и общий токен пересекаются в 0 парах, взаимное описание и взаимные рёбра — в 0, концентрация и токен — в 6 из 19. Поэтому это объединение, а не пересечение: одного сигнала достаточно, чтобы предложить пару, а веса (`--weight-about` и прочие) задают в основном порядок слияния почти непересекающихся списков, а не калибровку одной меры.

Оба вида рёбер несут сигнал — концентрация находит 10 кандидатов только по форвардам, 13 только по упоминаниям, 19 по обоим, — поэтому по умолчанию считаются оба; `--edge-kind` сужает.

**Хендл автора — не то же самое, что редкий токен, и добавлен он был именно поэтому.** Целая форма семьи оказалась невидимой сразу для всех четырёх сигналов: главный канал плюс спутники с общим суффиксом. Токенный сигнал молчит, потому что чем больше каналов автор держит под одним хендлом, тем больше этот хендл похож на тему: `1red2black` несут пять username при `--max-token-channels 3`. Поднять порог не помогает — в полосе «4–7 каналов на токен» вперемешку темы (`code`, `math`, `python`, `career`) и настоящие семьи (`nazarov`, `neurogen`, `ozon`), а формула `(M + 1 − d) / M` в точке `d = M` даёт минимум, так что искомая группа приходит в конец списка. Остальные три сигнала молчат по своим причинам: описание есть только у главного канала, у спутников слишком мало исходящих для знаменателя, а звезда «хаб → спутники» односторонняя по построению.

Различает их то, **подписан ли токен как хендл в описании самого носителя**. У `tg_1red2black` в описании стоит «Блоггер @1red2black», и это ровно тот токен, что несут пять username. По реальной базе (2057 username, 528 описаний) правило срабатывает на 9 группах и больше ни на чём — ни одно тематическое слово под него не попадает. Семь из девяти воспроизводят семьи, которые уже подтверждены руками; две добавляют новое.

Требование «называет носитель» — вся точность сигнала. Без него в группу попадает `@yandex`, названный чужим описанием и несомый 13 username, и 27 пар превращаются в 105.

Сила сигнала **не убывает** с размером группы: пять каналов, подписанных одним хендлом, не слабее двух. `--max-handle-token-channels` — предохранитель на число пар `d(d−1)/2`, а не порог редкости; на текущей базе он ничего не отсекает.

Хендл читается по более широкому шаблону, чем username: первым символом разрешена цифра, потому что `1red2black` — не username Telegram и всё равно подпись автора. Это безопасно ровно потому, что совпадение сверяется с замкнутым множеством токенов инвентаря: то, что не является ничьим токеном, не образует пары и никуда не попадает. В `derive/references.py` такое послабление стоило бы строки в `pending_mentions` и попытки резолва, поэтому там его нет и быть не должно.

**Подписанный токен читается один раз.** Если токен одновременно подписан и достаточно редок, вклад даёт только хендловый сигнал: оба читают одно и то же наблюдение, и складывать их значило бы посчитать один факт дважды.

Пары одного хендла печатаются блоком, а не вразброс по списку, и вместе с готовой строкой `itgraph family`: семья из пяти каналов — это девять пар и **одно** решение. `--limit` по-прежнему ограничивает пары, поэтому обрезанный блок сообщает, сколько его пар не показано.

### Как хранится семья

**Семья — множество без главного канала.** Никакой колонки: семья это связная компонента графа подтверждённых пар, и читается она через view `channel_families`. Каналов в семье может быть сколько угодно, а связи между ними — любые: `affiliates` находит среди группы одного автора произвольный граф пар, а не звезду.

```sql
SELECT channel_id, family_key FROM channel_families
```

Одна строка на канал, у которого есть хотя бы одна подтверждённая пара. Канала там нет — значит, он сам себе семья из одного, поэтому семья любого канала это `COALESCE(f.family_key, c.tg_id)`. Ребро внутри семьи — равенство двух таких ключей:

```sql
SELECT e.*
  FROM edges e
  JOIN channels s ON s.tg_id = e.src_channel_id
  JOIN channels d ON d.tg_id = e.dst_channel_id
  LEFT JOIN channel_families fs ON fs.channel_id = s.tg_id
  LEFT JOIN channel_families fd ON fd.channel_id = d.tg_id
 WHERE COALESCE(fs.family_key, s.tg_id) <> COALESCE(fd.family_key, d.tg_id)
```

Это и есть вычитание саморепостов: рёбра, у которых оба конца в одной семье, отбрасываются, а для неаффилированного большинства ключи разные и особого случая не нужно.

`family_key` — наименьший id в множестве. Это **метка компоненты, а не главный канал**: никакой код не выделяет этот канал, и наружу он не печатается. Прежняя модель с каноническим каналом убрана намеренно — она заставляла звезду там, где данные дают произвольный граф, и порядок подтверждения решал, что получится.

Ничего не хранится отдельно, поэтому ничто не может разойтись с парами. Слияние семей — это одна подтверждённая строка, распад — удаление строки; ни то, ни другое не реализовано отдельно, оба выпадают из вычисления.

**Рёбра внутри семьи не удаляются.** Репост действительно был; исключение — задача аналитики, а не деривации.

## YouTube

Англоязычный (и попутно русскоязычный) IT-YouTube, тем же порядком, что и Telegram: сначала инвентарь каналов, потом опрос, потом алерты. Что из этого уже есть, а что нет, — в `docs/PLAN.md`, раздел «YouTube».

Все команды YouTube собраны под `itgraph yt`:

```bash
uv run itgraph yt --help
```

Сессии, её блокировки и прокси здесь нет: YouTube Data API читается по ключу, и раздел про безопасность Telegram-аккаунта на YouTube не распространяется.

### Ключ

`YOUTUBE_API_KEY` в `.env`, а на хосте — вход роли `itgraph_youtube_api_key`. Секрет на тех же правах, что api hash: кто владеет ключом, тот тратит суточную квоту проекта. Ключ уходит в заголовке запроса и никогда в URL: httpx пишет в лог каждый URL.

Без ключа Telegram-команды и бот работают как прежде. YouTube-команды, которым нужна сеть, сразу отказываются и называют настройку. Офлайновые (`quota`, `channels`, `mark`, разметка файлом) работают и без ключа.

### Квота

10 000 единиц в сутки на проект; `channels.list`, `playlistItems.list` и `videos.list` стоят единицу за вызов, в том числе за невалидный. Сутки — гугловые: сброс в полночь по тихоокеанскому времени, это 10:00 по Москве летом и 11:00 зимой. Дважды в год сутки длятся 23 или 25 часов.

Каждый запрос сначала бронирует единицы в общей книге учёта в базе и только потом уходит. Поэтому две команды, запущенные одновременно, вместе не перерасходуют квоту. Единицы не возвращаются, даже если запрос упал: YouTube списывает и за ошибки.

| доля | сколько | кто тратит |
|---|---|---|
| запас | 10% | никто: страховка от расхождения нашего счёта с консолью Google |
| резерв опроса | 3 000 | только цикл опроса `yt watch` |
| общий пул | остальное, 6 000 | `yt add`, `yt refresh`, `yt backfill`, `yt tg-lookup`, `yt mention-lookup` |
| пул поиска | 90 вызовов (100 минус те же 10%) | только `yt search` |

Поиск (`search.list`) с 1 июня 2026 года считается в отдельном бакете Google: 100 вызовов в сутки по единице, вне 10 000. Поэтому у него свой пул и своя настройка, `YOUTUBE_SEARCH_DAILY_QUOTA`. `channelSections.list` стоит единицу из основного бакета, как остальные.

Пул определяется командой, а не выбором вызывающего кода: `yt watch` тратит только свой резерв, `yt search` — только пул поиска, остальные команды — только общий пул. Занимать друг у друга они не могут даже тогда, когда у соседа остаток есть.

Если YouTube ответил `quotaExceeded`, сутки кончились для всего бакета, к которому относится запрос, что бы ни показывал наш счёт. Основной бакет — это общий пул и резерв опроса вместе: до сброса ни одна YouTube-команда, кроме поиска, запрос не отправит. Бакет поиска — только поиск: исчерпанный поиск не останавливает цикл опроса, и наоборот. Ждать и повторять бесполезно. Как именно Google сообщает об исчерпании бакета поиска, не документировано. Если ответ окажется не `quotaExceeded`, команда просто остановится с ошибкой и ничего не пометит.

```bash
uv run itgraph yt quota
```

показывает траты за текущие сутки: по пулу, по команде и методу, и для каждого бакета — исчерпан ли он. Там же время сброса в UTC и по местным часам. `unknown` — запросы, которые забронированы, но ответа на них никто не дождался (процесс убили, связь оборвалась). Их единицы считаются потраченными.

### Обновление

Всё, что YouTube говорит о канале (название, handle, описание, подписчики), лежит отдельно от разметки. В YouTube-части базы две таблицы:

- `yt_channels` — наше: id канала и разметка. Хранится бессрочно и входит в ежедневный бэкап.
- `yt_raw_channels` — их: последний ответ API по каналу. Каждое обновление заменяет его.

Названия в `yt_channels` нет специально: в двух местах его пришлось бы держать свежим дважды.

- **Обновление.** `itgraph yt refresh` запрашивает заново всё, что старше 25 дней (`YOUTUBE_REFRESH_AFTER_DAYS`), по 50 каналов за единицу квоты. Обновляются все статусы, включая отклонённые: 500 каналов — это 10 единиц за цикл.
- **Пропавшие.** Если YouTube больше не возвращает канал, его ответ удаляется сразу, а канал помечается `gone` с датой. Разметка остаётся. Вернётся канал — пометка снимается при следующем обновлении.
- **Прошлые загрузки.** Пока включён проход истории (`YOUTUBE_BACKFILL_ENABLED`, см. «История загрузок: `yt backfill`»), `refresh` так же, по 50 за единицу, запрашивает заново каждое видео сида старше горизонта опроса и моложе глубины прохода (года), если его данные старше 25 дней. Это и найденное проходом, и то, что опрос дочитал до горизонта. Каждое такое обновление — ещё и снимок счётчиков. Видео старше года больше не запрашиваются и остаются такими, какими были прочитаны в последний раз. По замеру октября это 6–12 единиц в сутки на 100 каналов и 30–60 на 500. Выключен проход — прошлые загрузки не обновляются.

```bash
uv run itgraph yt refresh
# due 120, refreshed 119, gone 1, back 0
#   gone: UC...
```

На хосте `refresh` раз в сутки запускает CronJob `itgraph-yt-refresh` (05:00 по Москве), если в vault задан ключ. Пропущенный из-за простоя запуск стартует при включении, пока с момента расписания прошло меньше суток.

Если квота кончилась посреди обновления, всё обновлённое до этого уже записано, а следующий запуск продолжит с оставшегося. Команда при этом завершается с кодом 1, чтобы запуск по расписанию считался неудавшимся.

В лог `refresh` пишет только id каналов: журнал (`kubectl logs` на хосте) хранит записи сколько сочтёт нужным, и названиям там не место.

### Добавить каналы: `yt add`

Стартовый список собран руками из чужих подсказок, в том числе нейросетевых. Значит, в нём есть переименованные, мёртвые и выдуманные handle, а выдуманный handle может оказаться чужим настоящим каналом. Поэтому каждая запись сначала превращается в id канала через API, и только потом появляется запись в инвентаре. То, что не разрешилось, ничего не создаёт.

```bash
uv run itgraph yt add @fakehandle https://www.youtube.com/channel/UC...
uv run itgraph yt add --from-file seeds.txt --limit 50 --failures failed.txt
```

Формат файла — одна запись в строке. Пустые строки и `#`-комментарии пропускаются, комментарий можно ставить и после записи через пробел. Принимается:

- `@handle` и просто `handle`;
- `youtube.com/@handle` со схемой или без, с `www.`/`m.`, с хвостом вроде `/videos` или `?si=...`;
- `youtube.com/channel/UC...` и голый `UC...`;
- старые `youtube.com/user/NAME`.

Отбивается, причём сразу всё с номерами строк и **до** первого запроса:

- `youtube.com/c/NAME` и голый `youtube.com/NAME`: у API нет метода, который их разрешает, а угадать handle по имени значит рискнуть попасть в чужой канал;
- ссылки на видео, Shorts, стримы и плейлисты.

На всё это ответ один: открыть ссылку и скопировать `@handle` со страницы канала.

Что стоит квоты, а что нет:

- запись, на которую инвентарь отвечает сам (id уже есть, handle лежит в сохранённых данных канала), не стоит ничего, поэтому тот же файл после остановки продолжает с того же места;
- id идут по 50 за единицу, handle — по одному;
- `--limit` считает запросы, а не строки.

Записи создаются неразмеченными (`candidate`), и разметки `yt add` не ставит никогда: что handle теперь принадлежит кому-то другому, видит человек, глядя на результат, а не список, который этот handle назвал. Канал, который уже есть в инвентаре, `add` не трогает, только обновляет его данные.

`--failures PATH` записывает ненайденное тем же форматом с причиной в комментарии, так что этот файл годится как вход следующего запуска. `--failures -` пишет ненайденное в stdout, а отчёт в stderr, чтобы их можно было разделить через SSH (см. «Работа с хоста»).

### Работа с хоста

Рабочая база, бот и сбор живут на хосте, а разметка — работа объёмная и рутинная, её удобно делать на своей машине. Поэтому команда запускается на хосте, а её stdin и stdout приходят сюда:

```bash
scripts/on-host.sh yt channels
scripts/on-host.sh yt add --from-file - --failures - < seeds.txt > failed.txt
```

Хост берётся из `ITGRAPH_SSH`: ваша учётная запись на хосте, `вы@хост`, с sudo. Аргументы доезжают ровно такими, какими были набраны, вместе с пробелами и кавычками, а код выхода — код команды на хосте.

Это не туннель к Postgres. С туннелем здешний код мог бы обогнать схему на хосте, а `DATABASE_URL` переключался бы между рабочей базой и локальной: это та самая опасность «одна клавиша — две разные базы», от которой стоит `db/guard.py`.

Команда выполняется в отдельном Job, созданном из того, что оставила роль, поэтому исполняет развёрнутый образ, а не местный код. Job удаляется, когда команда заканчивается. Живёт он не дольше четырёх часов: команда, которая не уложилась, обрывается, а `backfill` при повторном запуске продолжит с того же места.

Командам, которым нужна сессия Telegram — `resolve`, `backfill`, `metadata`, — мешает коллектор: [сессию держит один процесс](#сессию-держит-один-процесс). Забытая остановка не авария — команда откажется сама и назовёт держателя, — но порядок такой:

```bash
scripts/on-host.sh --loop stop     # возвращается, когда пода коллектора уже нет: сессия свободна
scripts/on-host.sh --session resolve   # с сессией; ходит только через прокси неймспейса, как и сам коллектор
scripts/on-host.sh --loop start    # возвращается, когда коллектор снова готов, — тот же развёрнутый образ
```

Ожидание исчезновения пода — половина команды `stop`: без него следующая за ней команда соревнуется с выключением коллектора за сессию, которую первой и берёт.

### YouTube: разметка

Разметка идёт файлом, который выгружается с хоста, правится здесь в редакторе и отправляется обратно:

```bash
mkdir -p ~/itgraph-review
scripts/on-host.sh yt review-export > ~/itgraph-review/batch.review.tsv
# правим в VS Code / Sublime; каждый канал открываем по ссылке из последней колонки
scripts/on-host.sh yt review-apply - < ~/itgraph-review/batch.review.tsv
rm ~/itgraph-review/batch.review.tsv
```

По умолчанию выгружаются неразмеченные каналы. `--status maybe` выгружает отложенные вместе с тем, что про них уже решено.

Файл — TSV. Слева колонки, которые заполняются: `decision`, `kind`, `lang`, `reason`, `note`. Справа то, что помогает узнать канал: handle, название, подписчики, заявленные каналом язык и страна, ссылка и `source` — откуда канал взялся (`manual`, `telegram`, `mention`, `featured`, `search`; у найденного поиском — ещё и запрос самого раннего запуска за 30 дней, который его вернул). Счётов там нет: ни сидов, ни семей, ни результатов. Правые колонки при применении игнорируются. Файл, выгруженный до появления колонки `source`, `review-apply` отвергает как файл с изменённой строкой колонок: его надо выгрузить заново. В шапке — момент выгрузки и допустимые значения. Колонки разделены табами. Если редактор при сохранении заменяет табы пробелами, `review-apply` скажет об этом прямо: такую замену для `.tsv` надо отключить.

| колонка | значения | когда обязательна |
|---|---|---|
| `decision` | `seed`, `maybe`, `reject`, пусто | пусто — строка пропускается |
| `kind` | `personal`, `company`, `media`, `event`, `education` | для `seed` |
| `lang` | `en`, `ru`, `other` | для `seed` |
| `reason` | `not_it`, `adjacent`, `crypto`, `infobiz`, `ads`, `content_farm`, `consumer_tech` | для `reject`, и только для него |
| `note` | свободный текст | — |

`note` при отказе ложится в заметку к причине, иначе — в заметку к kind. Регистр значений не важен.

**Применение — всё или ничего.** Сначала проверяется весь файл. Seed без kind или языка, отказ без причины, опечатка в значении, неизвестный id, канал, указанный дважды, заполненные kind/lang/reason без решения — всё это выводится сразу с номерами строк, и пока ошибки остаются, не пишется ничего, в том числе правильные строки.

Если канал размечен (например, через `mark`) уже после выгрузки, его строка — **конфликт**: она не пишется, остальные применяются. Повторное применение того же файла ничего не меняет, даже время разметки.

Файл содержит собранные данные о каналах. Удалять его после применения — твоя часть работы. В репозиторий он не коммитится, и `.gitignore` ловит `*.review.tsv`, если файл всё-таки сохранили сюда.

Поштучно и чтобы поменять уже принятое решение — `mark`. Файл чужое решение не перезаписывает никогда. Чего не передали во флагах, `mark` не трогает: `--maybe` без `--kind` оставит прежний kind, язык и заметку, `--reject` — прежние kind и язык. Отличие от файла намеренное: файл показывает текущие значения, и пустая ячейка там значит «очистить», а `mark` ничего не показывает, поэтому пропущенный флаг значит «не трогать». Заметка к отказу идёт вместе с причиной: новый `--reject` без `--note` оставляет её пустой.

```bash
scripts/on-host.sh yt mark @fakehandle --seed --kind personal --lang en
scripts/on-host.sh yt mark UC... --reject --reason consumer_tech --note "обзоры телефонов"
scripts/on-host.sh yt mark UC... --maybe
scripts/on-host.sh yt channels                  # прогресс: статусы, языки сидов, свежесть данных
scripts/on-host.sh yt channels --status seed
```

Канал можно назвать по `UC...` id или по handle (с `@` или без, регистр не важен). Handle ищется в сохранённых данных канала, так что у канала без сохранённых данных работает только id.

#### Что такое kind

То, чем канал **является**, а не то, о чём он рассказывает. Правило то же, что в Telegram:

- `personal` — канал человека, в том числе того, кто учит;
- `company` — канал компании, в том числе devrel;
- `media` — редакция, издание;
- `event` — конференции, митапы, сообщества: на YouTube это архивы докладов;
- `education` — институция или издатель курсов (университет, freeCodeCamp-подобные).

Подкаст — формат, а не kind: подкаст человека — `personal`, подкаст компании — `company`.

#### Граница «айти»

| канал | решение |
|---|---|
| обзоры гаджетов, потребительская техника, сборка ПК, железо | `reject consumer_tech` |
| геймдев: девлоги, движки | `seed` |
| игры, обзоры игр | `reject not_it` |
| научпоп по CS и математике | `seed` |
| общий научпоп | `reject adjacent` |
| «заработай на нейросетях» | `reject infobiz` |
| безликие AI-каналы, перезаливы чужих докладов | `reject content_farm` |
| IT на третьем языке | `seed`, `lang other` — важна тематика, а не язык |
| канал, который давно ничего не выкладывает | не причина для отказа: активность увидим по видео |

Ферма контента, по ошибке пропущенная в сиды, не авария. Так в Telegram-боте нашлась слабость детектора разлетевшихся постов.

### Цикл опроса: `yt watch`

Один проход цикла: найти новые загрузки сидов и снять счётчики видео, у которых подошёл срок. На хосте проход запускает CronJob `itgraph-yt-watch` каждые 15 минут, если в vault задан ключ; частоту меняет переменная `itgraph_yt_watch_schedule` (формат cron), расписание — московское. Демона нет: каждый запуск — отдельный под, который делает свою работу и выходит; `Forbid` не даёт двум проходам идти одновременно. Зависший проход срубается по `activeDeadlineSeconds` — 10 минут, как было в `TimeoutStartSec` юнита systemd, — иначе он молча заблокировал бы все следующие.

```bash
uv run itgraph yt watch
# complete: 100 channels, listed 3, new 2, readings 14, removed 0
```

Что делает проход:

1. **Спрашивает про все сиды**, по 50 каналов за единицу квоты, и сразу обновляет их сохранённые данные. В ответе есть число публичных видео канала.
2. **Перечисляет загрузки** (`playlistItems.list`, единица за канал) только у тех каналов, у кого это число изменилось в любую сторону. Кроме того, раз в сутки — у каждого канала, что бы ни показывал счётчик: он лишь дешёвый сигнал. Загрузка и удаление в одном интервале его не сдвинут, а как быстро он обновляется, YouTube не документирует. Новое видео — неизвестное и опубликованное в пределах горизонта, 29 дней. Первый листинг канала поэтому забирает и недавние видео: их снимки начнутся с произвольного возраста, но это та самая поздняя часть кривой, которой иначе ждать четыре недели.
3. **Читает видео** (`videos.list`, 50 видео любых каналов за единицу): сначала только что найденные, потом все, у кого подошёл срок, от молодых к старым. Ответ обновляет сохранённое видео и даёт снимок счётчиков — просмотры, лайки, комментарии.

Сроки снимков: при обнаружении, затем в 1, 2, 4, 8, 12, 18, 24 и 36 часов и в 2, 3, 4, 5, 7, 10, 14, 21 и 28 дней. Возраст стрима считается от фактического начала эфира, остальных видео — от публикации. Пропущенный снимок не догоняется, как и в Telegram: возраст — факт каждой строки, а не номер в расписании. Запланированные эфиры не снимаются, пока не начались. Их проверяют в назначенное время и дальше раз в час, а через неделю после несостоявшегося старта бросают.

Опрашиваются все форматы — обычные видео, Shorts, стримы, премьеры. Формат нигде не записывается: его определяет скоринг. Недокументированные плейлисты вроде `UUSH` и запросы к сайту мимо API не используются.

**Почему счётчик, а не листинг всех каналов.** Листинг стоит единицу за канал и не батчится: 500 каналов раз в 15 минут — это 48 000 единиц в сутки при квоте 10 000. Через счётчик и суточную проверку выходит примерно 440–540 единиц в сутки на 100 каналов и 1 830–2 500 на 500, это внутри резерва 3 000. Оценка, а не замер: две недели `yt quota` покажут, так ли это.

**Где что лежит.** Видео — в `yt_raw_videos`, снимки — в `yt_raw_video_stats`, обе таблицы — в полном дампе. Расписание видео и то, как оно было найдено, лежат в той же строке, что и само видео, и уходят вместе с ним. Видео, которое YouTube перестал возвращать (удалено или скрыто), удаляется сразу вместе со всеми снимками. После горизонта опрос видео больше не читает; дальше его, пока ему меньше года, держит свежим `yt refresh` прошлых загрузок. Своё у цикла — `yt_channel_polls` (кому листинг должен, когда был, какие ошибки) и `yt_watch_passes` (что сделал каждый проход). Данных YouTube там нет.

**Темп и пустой пул.** Проход сравнивает потраченное за тихоокеанские сутки с равномерной долей резерва плюс 10%. Если цикл обгоняет график, суточные проверки и снимки видео старше недели откладываются, остальное идёт как обычно. Если пул кончился или YouTube объявил `quotaExceeded`, проход останавливается, сохраняет сделанное и выходит **с кодом 0**, называя время сброса. Это штатная ситуация, и запуску по расписанию незачем краснеть 30 раз до сброса. С кодом 0 выходит и проход, запущенный, пока идёт другой: два прохода дублировали бы снимки и тратили бы пул дважды, поэтому второй отказывается. Код 1 означает настоящую ошибку: YouTube ответил так, что работать нельзя, или нет ключа.

Блокировка прохода — своя, к сессии Telegram отношения не имеет: `yt watch` и Telegram-команды друг другу не мешают. Тихих часов нет: аккаунта, которому надо выглядеть человеком, здесь нет, а московская ночь — американский вечер, когда загрузок больше всего.

```bash
scripts/on-host.sh yt watch          # проход руками, с хоста
scripts/on-host.sh yt watch-status   # что отслеживается и что сделал последний проход
# 214 video(s) tracked, 3 due now
# watch pool: 1210 of 3000 units today, on pace
# found in 7 days: 31 by the video count, 2 by the daily check, 0 by first listings
# last pass 2026-10-27 09:15 UTC, complete: listed 2, new 1, readings 9, removed 0
```

Строка `found in 7 days` — главная проверка выбранной схемы: всё, что нашла суточная проверка, счётчик пропустил. Если таких много, схему обнаружения пора пересматривать.

**Первый запуск.** Первый проход перечисляет загрузки всех сидов сразу: 100–500 единиц разом, внутри пула. Запустите его руками и посмотрите `yt watch-status` и `yt quota`: так подтвердится, что YouTube принимает наши `fields`, как приходят скрытые счётчики и сколько стоит первый листинг. Таймеру стоит доверять после этого.

В лог проход пишет только id каналов и видео.

**Сколько хранится.** Всё, без срока: и видео, и снимки. Удаляется только то, что YouTube перестал возвращать.

### История загрузок: `yt backfill`

Опрос видит у канала последние 29 дней — около 650 видео на сотню сидов. Граф упоминаний и поиск новых каналов читают, кого канал упоминает и на кого ссылается, а за год загрузок это примерно в двенадцать раз больше. Поэтому плейлист загрузок каждого сида один раз проходится вглубь, на год по умолчанию (`YOUTUBE_BACKFILL_DAYS`), а дальше год сдвигается сам: спереди его пополняет опрос, `yt refresh` держит его свежим, а сзади видео старше года истекают.

```bash
scripts/on-host.sh yt backfill                         # все сиды, ещё не пройденные
scripts/on-host.sh yt backfill @fakehandle --whole     # названные каналы, до конца плейлиста
scripts/on-host.sh yt backfill --limit 100             # не больше ста запросов
scripts/on-host.sh yt backfill-status
```

**Что делает проход.** Листает загрузки канала страницами по 50 (`playlistItems.list`, единица за страницу) и на каждую страницу спрашивает видео (`videos.list`, ещё единица). Останавливается на странице, где появилось первое видео старше глубины: страница всё равно оплачена целиком. С `--whole` идёт до конца плейлиста, но сохраняет тоже только то, что внутри глубины. Так проверяется порядок, на который опирается остановка. Каждая страница записывается вместе с видео, до которых она довела. На канал — не больше `YOUTUBE_BACKFILL_MAX_VIDEOS` видео (1 000; 0 — без потолка). Сегодня самый плодовитый сид выкладывает около 590 видео в год, так что потолок пока ничего не режет.

**Порядок проверяется, а не принимается на веру.** Что плейлист загрузок идёт от новых к старым, YouTube нигде не пишет. Первая страница действительно самая новая: это видно по данным опроса. Про следующие страницы известно только то, что посчитает сам проход: каждое видео новее уже пройденного, каждый элемент без даты, каждое видео, которое `videos.list` не вернул. Это три числа в `backfill-status`. Элемент без даты проход не пропускает, а спрашивает: это может быть ещё не начавшийся эфир.

**Что проход оставляет опросу.** Видео моложе горизонта опроса (29 дней) проход не трогает: их находит и читает `yt watch`. Видео, уже лежащее в базе, он не спрашивает заново и никогда не перезаписывает. Запланированный эфир, который листинг датирует старше горизонта, опрос сам никогда бы не увидел. Проход кладёт его с `due_at` на время старта, и дальше это видео опроса: тот проверит его в начале эфира, будет читать по своему расписанию и бросит через неделю, если эфир так и не начался. Путь находки у такого видео остаётся `backfill`.

**Каждое видео — ещё и снимок.** Проход спрашивает видео со `statistics`, и каждое видео, которое сохранил проход или обновил `refresh`, становится и снимком (`yt_raw_video_stats`) из того же ответа: это зрелый уровень канала, нужный скорингу.

**Где что лежит.** Видео — в `yt_raw_videos`, с путём `backfill` и `due_at` NULL. Своё у прохода — `yt_backfill_walks`, по строке на канал: когда пройден, до какого момента, сколько страниц и видео, три счётчика выше, упёрся ли в потолок, последняя ошибка. Данных YouTube там нет, ни одной даты видео. Обе таблицы — в полном дампе. Запись о проходе забывается, когда канал перестаёт быть сидом (через `mark` или файл разметки) и когда YouTube перестаёт его возвращать. Канал, снова ставший сидом, проходится заново.

**Включатель.** `YOUTUBE_BACKFILL_ENABLED`, на хосте — `itgraph_youtube_backfill_enabled` в настройках роли (`deploy/ansible/itgraph/defaults/main.yml`). В коде по умолчанию `false`, на хосте включён с графом упоминаний (change 4). Если его выключить:

- CronJob'а `itgraph-yt-backfill` нет, ничего не проходится само;
- `yt refresh` не обновляет прошлые загрузки: они остаются такими, какими были прочитаны.

Проход руками работает и при выключенном включателе — так делается проверочный прогон. Включён он вместе с графом упоминаний (`yt mentions`, ниже), его первым читателем. Включённый, он ставит CronJob `itgraph-yt-backfill` (11:30 по Москве, после сброса квоты в любой сезон), который каждый день проходит сиды, ещё не пройденные, а `yt refresh` держит пройденное свежим.

**Квота.** Проход тратит общий пул и оставляет в нём `YOUTUBE_BACKFILL_GENERAL_FLOOR` единиц (2 000) для `yt add`, `yt refresh` и будущего поиска каналов. Порог проверяется при бронировании, тем же условным `UPDATE`, что и потолок пула. По замеру октября (105 сидов, 0,22 загрузки на канал в сутки) год стоит около 430 единиц на 100 каналов и 2 140 на 500, при вдвое большем темпе — 740 и 3 680. Это один запуск на сотню каналов и сутки на пятьсот. Блокировка у прохода своя: ни опрос, ни Telegram-команды он не задерживает и сам от них не ждёт.

**Выходы.** Порог, исчерпанный пул, `--limit` или `quotaExceeded` останавливают проход **с кодом 0**: сделанное сохранено, следующий запуск продолжит. С кодом 0 выходит и проход, запущенный, пока идёт другой. Код 1 означает настоящую ошибку: запрос не удался после всех попыток, YouTube ответил так, что работать нельзя, или нет ключа. Канал, на котором проход остановился, остаётся непройденным, и следующий запуск пройдёт его снова с первой страницы. Токен страницы между запусками не хранится — сколько он живёт, YouTube не пишет. Уже сохранённые видео при этом не перезапрашиваются, так что повтор стоит только страниц листинга. Канал, чей плейлист не нашёлся (404) или закрыт (403), записывается как ошибка этого канала, и проход идёт дальше.

**Первый запуск.** Выбрать пять сидов, у которых меньше 300 видео, и пройти их целиком:

```bash
scripts/on-host.sh yt backfill UC... UC... UC... UC... UC... --whole
scripts/on-host.sh yt backfill-status
scripts/on-host.sh yt quota
```

Это около 25 единиц. Ноль в «out of order» подтверждает порядок, на который опирается остановка. «undated» и «not returned» показывают, как API отдаёт удалённые, скрытые и запланированные видео. Если порядок нарушен — сначала разбираться, потом включать проход по расписанию.

В лог проход пишет только id каналов и видео.

### Виральность YouTube: `yt baselines` и `yt score`

То, что делают `baselines` и `score` для Telegram, но для видео: видео оценивается против своего канала, своего формата и своего возраста.

```bash
uv run itgraph yt baselines   # пересчитать, что для канала нормально
uv run itgraph yt score       # найти всплески, записать оповещения
```

Ключ YouTube не нужен ни одной из команд: обе читают только сохранённые видео и показания, в YouTube не ходят и квоту не тратят. На хосте `yt baselines` запускает CronJob `itgraph-yt-baselines` в 05:30, после `yt refresh`, а `yt score` — `itgraph-yt-score` каждые 15 минут, через шесть минут после прохода `yt watch`. Оба работают в любом окружении, тестовом тоже.

**Что оценивается.** Видео сидов с языком `en` или `ru`: канал с языком `other` оповещений не получает, поэтому и не оценивается. Канал — тот, которому YouTube приписывает видео сейчас. Три сигнала — просмотры, лайки, комментарии, каждый против своей кривой. Счётчик, который YouTube не показал (скрытые лайки, закрытые комментарии), не оценивается и нулём не считается.

**Два формата.** Короткие — без данных эфира и не длиннее 180 секунд (`youtube_scoring_short_max_seconds`, предел Shorts), длинные — все остальные без данных эфира. Флага «это Shorts» в API нет. По замеру видео на 61–180 секунд ведут себя как минутные, а не как длинные, а `#shorts` стоит лишь у каждого восьмого короткого видео. У канала две опоры — для коротких и для длинных: просмотры Shorts и докладов несравнимы. Стримы и премьеры (у них есть `liveStreamingDetails`) не оцениваются. Видео без читаемой длительности тоже. Проход считает и те, и другие.

**Возраст — от трёх часов до восьми с половиной дней.** Полосы сплошные, в каждой одно плановое чтение цикла опроса: 4, 8, 12, 18, 24, 36 часов, 2, 3, 4, 5 и 7 дней. Раньше трёх часов не оцениваем: счётчик просмотров в первые часы отстаёт — на первом часу у каждого десятого видео ноль, между чтениями на втором часу он стоит на месте у четверти. Позже восьми с половиной дней оповещений нет.

**Опора канала.** Медиана значения в возрасте суток (полоса 21–30 часов) у его 20 последних видео этого формата не старше 180 дней, если их не меньше 10 (`youtube_baseline_recent_*`). Для комментариев — среднее вместе с нулями. Каналам, у которых столько своих видео нет, — запасная опора: медиана их зрелых видео, по одному чтению на видео — последнему в возрасте 29–120 дней (`youtube_baseline_mature_*`), не меньше 10 видео, умноженная на фактор вида канала. Зрелые чтения дают `yt refresh` раз в 25 дней и обход истории. У комментариев запасной опоры нет, как и в Telegram.

**Кривые и разброс** — по виду канала и формату. Вид, которому не хватает данных, берёт общую кривую своего формата, и пересчёт это отмечает (`borrowed`). Разброс — по возрастным полосам, собственный только у полосы, где не меньше 100 разных видео.

**Одно видео — одно оповещение на сигнал**, по самой сильной оценке. Оповещение указывает на то чтение, с которого эта оценка, и сообщение берёт оттуда число комментариев. **Всплески одного канала за сутки** (`youtube_alert_spike_fold_hours`, 24 ч) — одно событие. Первый уходит сообщением, остальные сворачиваются в него. Так конференция, выложившая пачку докладов, присылает одно сообщение, а не десять. Сутки, а не шесть часов, как в Telegram: чтения видео разнесены на часы и дни, и видео одного события переходят порог на разных плановых возрастах.

**Порог свой** — `youtube_alert_spike_z`, один для обоих языков, вместе с минимумом комментариев `youtube_alert_spike_comments_min`: 3.0 и 10. Порог подобран повтором 2–12 ноября 2026, таблица — в `docs/PLAN.md` («YouTube», «Scoring»): при нём около трёх английских сообщений в сутки, внутри задуманных 2–5, и почти все пересечения держатся. Минимум комментариев пока телеграмный: в том повторе комментарии не перешли порог ни при каком минимуме.

**Повтор.**

```bash
uv run itgraph yt score --replay                                   # что бы сработало за две недели
uv run itgraph yt score --replay --threshold 3.7 --threshold 4.5   # два порога за один прогон
uv run itgraph yt score --replay --comments-min 5                  # другой минимум комментариев
uv run itgraph yt score --replay --since 7 --list                  # за неделю, с каждым видео
```

В отличие от повтора Telegram, базовые линии здесь пересчитываются в памяти на начало каждого дня (по Москве), и день оценивается против своих. Иначе при паре недель данных кривые подгонялись бы на тех же днях, которые оцениваются. Повтор ничего не пишет. Он печатает, сколько сообщений, пересечений и свёрнутых вышло бы по языкам и по дням, сколько пересечений у каждого сигнала и формата, разрывы между пересечениями одного канала (на них меряется окно свёртки). С `--list` — каждое видео по id, его z, фактическое и ожидаемое значение, а у свёрнутого — во что он свёрнут.

**«Выстрелило» повтор проверяет сам, а не на глаз.** Каждое пересечение он доводит до последнего показания видео:
- **держится** (held) — показанию не меньше трёх дней, а видео всё ещё минимум вдвое выше того, что видео канала этого формата набирают к этому возрасту;
- **откатилось** (faded) — показание такое же старое, но видео вернулось ближе к норме. Обычно это догнавший счётчик, угасший всплеск или полоса со слишком узким разбросом;
- **рано судить** (too early) — показания старше трёх дней ещё нет.

Доли видны по каждому языку рядом с объёмом. Порог выбирается так: самый низкий, при котором объём укладывается в задуманный и пересечения в основном держатся. Три дня и «вдвое» — только мерило для выбора, живой проход их не читает. Без флага дни раньше 12 ноября 2026 в счёт не идут: зрелые показания прошлых загрузок появились 11-го, а день видит только то, что снято до его начала. `--late-settled` разрешает каждому дню брать зрелые показания, снятые позже, до конца окна повтора, — и только их. Зрелые видео — месячные и старше, это не те видео, что оцениваются, так что подсказки «из будущего» о них нет. Цена — зрелое видео прочитано на несколько дней старше, чем было бы; видео такого возраста этого почти не замечает, а фактор подгоняется по тем же медианам и сдвиг поглощает. Отчёт пишет, что флаг был. Первый подбор порога идёт по 2–11 ноября с ним, калибровка позже — без него.

Итоговая строка прохода, как в Telegram, различает «ничего не случилось», «канал не оценивается» и «канал оценивается по зрелым видео». Отдельно она называет эфиры и видео без длительности, которые пропустила.

### Список недели: `yt weekly`

Раз в неделю, по каждому языку, — каналы, чьи видео за неделю лучше всего превзошли их обычный уровень.

```bash
uv run itgraph yt weekly                          # списки последней закончившейся недели
uv run itgraph yt weekly --preview                # то же по id, ничего не пишет
uv run itgraph yt weekly --week 2026-11-16        # другая закончившаяся неделя, по её понедельнику
```

Ключ YouTube не нужен: команда читает только сохранённые видео, показания и пересчёты баз. На хосте её запускает CronJob `itgraph-yt-weekly` по понедельникам в 10:00; пропущенный запуск догоняется в течение шести дней и считает всё ту же закончившуюся неделю. Работает в любом окружении, тестовом тоже, и шлёт там в свой чат.

**Неделя** — с понедельника 00:00 до следующего понедельника 00:00 по Москве, по дате публикации видео. Каждое видео попадает не больше чем в один список. Показания берутся до момента расчёта: у видео воскресного вечера к понедельнику есть часы чтений, у видео прошлого понедельника — семь дней. Оценка учитывает возраст, так что молодое видео не проигрывает за молодость, но разброс у него шире.

**Оценка — как у живого прохода.** Каждое показание сравнивается с пересчётом баз, который был самым новым в момент показания: именно против него его оценил проход `yt score`. Поэтому пересчёты не удаляются. Показание, снятое раньше первого пересчёта, не оценивается и считается в итоге. Сигналы и минимум комментариев — те же, что у оповещений. Эфиры и видео без длительности не оцениваются.

**Одна запись на канал.** Видео выше порога, если его лучшая оценка не ниже `youtube_weekly_list_z` (2.0). Канал попадает в список своим лучшим таким видео, остальные его видео выше порога считаются («ещё 2 видео канала выше нормы»). Каналы — по убыванию оценки; при равенстве раньше тот, кто раньше перешёл порог, затем по id видео. В списке не больше `youtube_weekly_list_size` (10) каналов. Если выше порога меньше — список короче; ниже порога ничего не добирается. Shorts и длинные видео идут вместе, Shorts помечены. Язык — метка канала в момент расчёта: посчитанный список уже не переезжает между топиками.

**Что хранится.** `yt_weekly_lists` — неделя, язык, момент расчёта, параметры, сколько видео оценено и сколько каналов выше порога, доставка. `yt_weekly_entries` — ранг, канал, видео, показание, сигнал, оценка, ожидание, сколько ещё видео канала выше порога. Ни названий, ни счётчиков YouTube: их бот читает при отправке, как у оповещений. Запись уходит вместе со своим показанием. Повторный расчёт той же недели ничего не пишет и говорит об этом.

**Сообщение.** Бот шлёт список в топик его языка: не в счёт дневного лимита, не в дайджест, после тихих часов, без превью ссылки, частями, если не помещается в одно сообщение. Отправленную часть он отмечает, поэтому упавшая часть уходит снова, а уже отправленные — нет; заголовок продолжения так и говорит. В каждой записи — то же, что обещает сайт для оповещения: ссылка на видео на YouTube, название, канал, возраст, счётчики YouTube со временем их чтения и оценка itgraph, подписанная как оценка itgraph. Для просмотров и лайков — во сколько раз выше обычного: список хранит ожидание, против которого считалась оценка. Для комментариев — число и обычное. Неделя, где выше порога ничего, тоже отправляется: «Выше нормы — ничего», с числом оценённых видео. Так «ничего не выстрелило» отличается от «ничего не оценено».

**Проверка на копии.** Восстановление закрывает неотправленные списки как отправленные и проверяет это; потом гоняет `yt weekly --preview` на восстановленных данных. Превью ничего не пишет, так что плановый расчёт на копии не вытесняется.

### Упоминания: `yt mentions`

На кого сиды ссылаются и кого упоминают в названиях и описаниях своих видео — и прошлых, и новых. Без сети и без ключа.

```bash
scripts/on-host.sh yt mentions                 # всё, по 50 строк в списке
scripts/on-host.sh yt mentions --min-seeds 2   # только то, что называют хотя бы два сида
scripts/on-host.sh yt mentions --limit 0       # без ограничения строк
```

**Ничего не хранится.** Граф не хранится нигде: команда каждый раз разбирает те payload'ы, что лежат в базе сейчас. Описание поменялось и обновилось — ссылка пропала. Видео удалено — вместе с ним пропало всё, что из него следовало. Команда ничего не пишет в базу.

**Что читается.** Названия и описания видео сидов — найденных и опросом, и проходом истории, — и списки избранных каналов (featured) сидов, которые читает `yt refresh`. Канал из такого списка — ссылка самого сида, формы `featured`, без видео. Видео каналов в других статусах и описания каналов не читаются. Описания каналов дали две новые цели на 101 описание, а их чтение потребовало бы менять сайт.

**Что считается ссылкой.**

- На канал: `youtube.com/@хендл`, `youtube.com/channel/UC…`, `youtube.com/user/имя` — с `www.`, `m.`, `music.`, со схемой или без, с любым хвостом.
- На видео: `watch?v=`, `youtu.be/`, `/shorts/`, `/live/`, `/embed/`, `/v/`, `youtube-nocookie.com`. `list=`, `t=` и `si=` отбрасываются.
- Голое `@хендл` — только если такой хендл есть у канала в инвентаре. Голые `@` в этих описаниях — в основном аккаунты людей в X и других местах: с хендлами инвентаря они совпадают в 5–47 раз реже, чем ссылки. Поэтому незнакомое голое `@` в очередь не идёт, а только считается. Каждый новый канал в инвентаре сам превращает упоминания себя в рёбра.

Хендл читается по правилам YouTube: буквы и цифры любой письменности, `_ - . ·` внутри, от 3 до 30 символов, регистр не важен. `@scope/package`, адреса почты и ссылки самого канала на себя ссылками не считаются.

**Что получается.** Известная цель — канал из инвентаря или сохранённое видео — даёт ребро. Неизвестная становится целью для change 5, вместе с сидами, которые её называют: хендл, старое имя (`/user/`), id канала или id видео. Записей в инвентаре команда не создаёт. Оба списка идут по числу разных сидов: это единственное число, которое считается по графу. Весов, рангов и кластеров для YouTube пока нет.

**«not followed».** Что посчитано, но не прочитано:

- `custom URLs` — `/c/имя` и `youtube.com/имя`: API их не находит, а угадывать хендл по имени — значит попасть в чужой канал;
- `playlist pages` — владельца плейлиста знает только `playlists.list`, которого нет среди методов на сайте;
- `shortened links` — раскрыть короткую ссылку значит сходить не к YouTube;
- `Telegram links` — только число: искать телеграмные каналы по данным YouTube — цель, которой сайт не заявляет, поэтому имена не выводятся;
- `mentions outside the inventory` — голые `@`, о которых выше.

**Никогда по расписанию.** Команда печатает хендлы — данные YouTube. Вывод CronJob'а кластер хранит в логах, так что её запускают только руками, через `scripts/on-host.sh`. Вывод не сохраняйте в репозиторий. Тест манифестов проверяет, что ни один CronJob её не запускает. В лог команда пишет только id и счётчики.

### Каналы из Телеграма: `yt tg-lookup` и `yt tg-candidates`

На какие YouTube-каналы ссылаются телеграм-сиды — по числу разных семей, — и топ из тех, которых ещё нет в инвентаре, кандидатами на разметку. Посты уже лежат в `raw_messages`: сессия Телеграма не нужна, цикл сбора останавливать не надо.

```bash
scripts/on-host.sh yt tg-lookup --limit 5      # первый прогон: пять запросов
scripts/on-host.sh yt quota                     # чем они кончились
scripts/on-host.sh yt tg-lookup                 # всё, что ждёт lookup; повторять, пока не останется 0
scripts/on-host.sh yt tg-candidates             # рейтинг: топ-100 и одна строка про остальных
scripts/on-host.sh yt tg-candidates --top 30 --min-families 3
scripts/on-host.sh yt tg-candidates --add       # топ-100 → кандидаты с источником telegram
scripts/on-host.sh yt refresh                   # их данные; иначе придут с ночным refresh
scripts/on-host.sh yt review-export > ~/itgraph-review/telegram.review.tsv
```

**Что читается.** Собственные посты каналов со статусом `seed`, кроме чатов, за всю собранную историю. Ссылки — только из трёх мест: размеченные Телеграмом ссылки в тексте, ссылки под текстом и URL превью. Ссылки разбираются по грамматике `yt mentions`, по одной.

Не читается:

- текст, который Телеграм ссылкой не разметил;
- заголовок, описание, автор и сайт превью: по ним канал не опознать надёжно;
- `@имя` — в Телеграме это юзернейм, а не хендл YouTube;
- пересланные посты, от кого бы ни были. Ссылку в посте выбирает автор, а переславший одобрил пост, не ссылку. Подпись «мой YouTube» под разошедшимся постом иначе собрала бы все семьи, которые его переслали. Если автор — сид, его собственный пост и так читается.

`/c/имя` и `youtube.com/имя` API не разрешает: имена печатаются в отчёте с числом семей — хендл можно найти руками и добавить через `yt add`, уже как `manual`. Плейлисты и короткие ссылки только считаются.

**Единица — семья.** Аффилированные каналы одного автора — одна семья, канал вне семей — семья сам по себе. Сколько бы постов, ссылок и каналов одной семьи ни ссылались на YouTube-канал, это одна семья. Ссылка на видео засчитывается его каналу.

**`yt tg-lookup` — единственная сетевая часть.** Чей канал — видео, хендл, старое имя (`/user/`) — спрашивается только то, на что не отвечает ничего сохранённого: id канала отвечает сам за себя, сохранённое видео — своим payload'ом, хендл — payload'ом канала из инвентаря (если его несёт ровно одна запись), остальное — lookup моложе `YOUTUBE_ANSWERS_FRESH_DAYS`. Запрос — только id: у видео `items(id,snippet/channelId)`, у хендла и имени `items(id)`. Видео по 50 за единицу, хендл и имя по единице. Первыми идут имена, на которые ссылается больше семей, так что `--limit` (он считает запросы) тратит на самое важное. Каждый ответ, «не найдено» тоже, сохраняется до следующего запроса, поэтому остановка по `--limit`, по квоте или по ошибке ничего не теряет, а следующий запуск продолжает. Общий пул, без пола: пол оставляет backfill как раз для таких команд.

Ответы лежат в `yt_raw_lookups`. Ответ старше `YOUTUBE_ANSWERS_FRESH_DAYS` (30 дней по умолчанию) больше не читается, и следующий `tg-lookup` спросит его заново. Кто на какой канал ссылается, не хранится нигде: это соединение постов Телеграма с ответами API, и оно считается при каждом чтении.

**`yt tg-candidates` — без сети и без ключа.** Каналы вне инвентаря — в любом статусе, `gone` тоже — по числу семей, при равенстве по самому свежему посту со ссылкой, потом по id. По умолчанию — от двух семей и топ-100. В строке: id канала, хендл или имя, как его написал Телеграм, число семей и дата самого свежего поста. Ни названий, ни подписчиков: их показывает файл разметки. Ниже — сколько ссылок ждёт lookup, сколько не нашлось, имена `/c/`, плейлисты и короткие ссылки.

`--add` создаёт показанный топ кандидатами (`candidate`, источник `telegram`) без разметки и без данных. Отказывается, пока хоть одна ссылка ждёт lookup: иначе отсечка шла бы по половине доказательств. Данные новых записей приносит `yt refresh` — две единицы на сотню. Кто уже в инвентаре, не предлагается никогда, а записи не удаляются, поэтому отклонённые не вернутся, а следующий `--add` даст следующую сотню. Так добираются англоязычные: топ в основном русскоязычный, а язык виден только при разметке.

**Первый прогон.** `--limit 5` и `yt quota`: справка не говорит, как `videos.list` отвечает на батч с удалённым видео. Если батчи падают целиком в 404, код переспрашивает каждое видео отдельно — до 50 единиц вместо одной. На старых постах таких видео много, и тогда прогон упрётся в потолок пула. Вторая неизвестная — кириллический хендл в `forHandle`: если не найдётся, это будет видно в счётчике «not found».

**Никогда по расписанию.** Отчёт показывает, на что ссылаются собственные подписки оператора, а вывод CronJob'а кластер хранит в логах. Обе команды запускают только руками, тест манифестов это проверяет. Вывод не сохраняйте. В лог пишутся только id и счётчики, а строки httpx с URL — в них хендл — на время `tg-lookup` отключены.

Первый прогон 1 ноября ответил на вопрос про батчи: ни один батч видео не упал целиком в 404, удалённые видео просто отсутствовали в ответе, а число вызовов равнялось числу видео, делённому на 50.

### Раунд до 500: четыре очереди кандидатов

Цель — 500 англоязычных сидов (решено 1 ноября; русскоязычные идут попутно и в счёт не входят). Каналы приходят из четырёх очередей. У каждой свой отчёт, своё `--add` и свой источник в `discovered_via`, поэтому выход каждого источника видно прямо в инвентаре. Общего рейтинга нет: складывать семьи Телеграма с сидами YouTube значило бы строить новую метрику частично из данных API.

| очередь | что считается | порог по умолчанию | сеть | источник |
|---|---|---|---|---|
| `yt tg-candidates` | разные семьи телеграм-сидов, ссылающиеся на канал | 2 семьи | `yt tg-lookup` | `telegram` |
| `yt mention-candidates` | разные сиды, чьи видео ссылаются на канал (после lookup) | 2 сида, потом 1 | `yt mention-lookup` | `mention` |
| `yt featured-candidates` | разные сиды, у которых канал в избранных | 1 сид | `yt refresh` | `featured` |
| `yt search-candidates` | ничего: порядок выдачи YouTube, запрос за запросом по очереди | результаты в пределах `YOUTUBE_ANSWERS_FRESH_DAYS` | `yt search` | `search` |

Канал, у которого уже есть запись, — в любом статусе, `gone` тоже — не предлагает ни одна очередь. Отклонённые не возвращаются. Канал из нескольких очередей попадает в инвентарь один раз — через первое `--add`, которое до него дошло.

**Раунд по шагам.**

```bash
# 1. Featured-списки: их читает ночной refresh, одна единица на сид.
scripts/on-host.sh yt refresh
scripts/on-host.sh yt featured-candidates

# 2. Упоминания: сначала lookup, потом отчёт.
scripts/on-host.sh yt mention-lookup --limit 5
scripts/on-host.sh yt quota
scripts/on-host.sh yt mention-lookup               # пока не останется 0
scripts/on-host.sh yt mention-candidates           # от двух сидов
scripts/on-host.sh yt mention-candidates --min-seeds 1

# 3. Поиск: запросы — по одному на строку, из файла на этой машине.
scripts/on-host.sh yt search --from-file - --limit 5 < ~/itgraph-review/queries.txt
scripts/on-host.sh yt quota                         # строка search
scripts/on-host.sh yt search --from-file - < ~/itgraph-review/queries.txt
scripts/on-host.sh yt search --type channel --from-file - < ~/itgraph-review/queries.txt
scripts/on-host.sh yt search-candidates

# 4. Кандидаты — примерно сотня на весь раунд, из нескольких очередей.
scripts/on-host.sh yt featured-candidates --add --top 30
scripts/on-host.sh yt mention-candidates --add --top 30
scripts/on-host.sh yt search-candidates --add --top 40
scripts/on-host.sh yt refresh                       # их данные
scripts/on-host.sh yt review-export > ~/itgraph-review/round.review.tsv
# разметка; потом
scripts/on-host.sh yt review-apply - < ~/itgraph-review/round.review.tsv
rm ~/itgraph-review/round.review.tsv
```

Новые сиды на следующую ночь проходит `yt backfill`: их описания и featured-списки дают кандидатов следующего раунда.

**Что сколько стоит.** Featured — единица на сид раз в 25 дней, из общего пула, внутри ночного refresh. `mention-lookup` — единица на хендл или старое имя и единица на 50 видео; первый прогон около 170 единиц, потом только то, что устарело и всё ещё нужно. Поиск — единица на страницу из 50 результатов, из своего пула в 90 вызовов в сутки, вне 10 000. Проход истории для новых сидов — 4,5–9 единиц на сид, за ночь.

**Поиск.** Запросы — твои слова. Файл лежит у тебя, в репозиторий не обязателен, личных данных в нём нет. Пустые строки и строки, начинающиеся с `#`, пропускаются; больше комментариев нет, так что «C# tutorial» — это запрос. По умолчанию `--type video`: загрузки за последние `YOUTUBE_ANSWERS_FRESH_DAYS` (30 дней), значит, каждый найденный канал публикует сейчас, а оповещениям нужны свежие видео. `--type channel` находит каналы по их собственным данным, включая заброшенные. Язык — английский (`relevanceLanguage=en`). Читается только id канала каждого результата. Запрос того же типа, уже заданный в этом окне, пропускается бесплатно; `--force` задаёт его снова — для видео только с момента прошлого запуска. В первом раунде задай одни и те же запросы обоими типами и сравни выход: какой тип чаще даёт англоязычных сидов, тот и становится основным.

**Выход раунда.** После разметки запиши в `docs/PLAN.md`, «Rounds to 500», агрегаты: сколько каналов каждого источника в каждом статусе и с каким языком. Только числа — read-only SQL по `yt_channels`:

```sql
BEGIN TRANSACTION READ ONLY;
SELECT discovered_via, status, coalesce(lang::text, '-') AS lang, count(*)
FROM yt_channels GROUP BY 1, 2, 3 ORDER BY 1, 2, 3;
ROLLBACK;
```

**Никогда по расписанию.** Отчёты, их `--add`, lookup упоминаний и поиск — шаги раунда, которые человек читает. Поиск к тому же читает твой файл и тратит свой бакет. Тест манифестов проверяет, что ни один CronJob их не запускает. Единственная автоматическая часть — featured-списки внутри ночного `yt refresh`. В логах только id и счётчики: запросы поиска и хендлы туда не попадают.
