# Развёртывание

Ansible-плейбук, поднимающий сбор на чистой Ubuntu: docker с Postgres,
`watch`, бот и четыре таймера — `derive && alerts`, `score`, ежедневный
`baselines` и копии.

Все команды — из корня репозитория: `ansible.cfg` лежит там, и Ansible
читает его только из текущего каталога.

```bash
ansible-galaxy install -r deploy/requirements.yml
cp deploy/inventory.ini.example deploy/inventory.ini            # вписать адрес и пользователя
pbpaste > deploy/.vault_pass && chmod 600 deploy/.vault_pass    # пароль vault из менеджера паролей
$EDITOR deploy/group_vars/all/main.yml                          # репозиторий, пути к сессии и дампу

ansible-playbook deploy/playbook.yml
```

Секреты приезжают с клоном зашифрованными — см. «Секреты» ниже.

Перед первым запуском снимите свежий дамп на рабочей машине — `watch` всё
ещё пишет, и вчерашний уже отстал. Снимайте **после** остановки `watch`:
дамп, снятый до неё, отстанет ровно на то время, что уйдёт на
развёртывание, а пропущенные снимки счётчиков не восстанавливаются.

```bash
make backup-full
```

`itgraph_dump_src` указывает на `weekly/full-LATEST.dump` — симлинк, который
обновляется на последний проверенный дамп. Имя файла руками подставлять не
нужно; это тот выбор, на котором ошибка означает развёртывание со старого
дампа.

## Таймеры и почему их четыре

| юнит | как часто | что делает |
|---|---|---|
| `itgraph-alerts` | 15 мин | `derive`, затем `alerts` — каскады репостов |
| `itgraph-score` | 15 мин | всплески просмотров, реакций и пересылок |
| `itgraph-baselines` | каждый день, 04:30 | пересчёт того, что для канала нормально |
| `itgraph-backup` | 4 ч | дампы |

`score` — **отдельный юнит, а не третий `ExecStart` у `itgraph-alerts`**.
Тот юнит — oneshot из двух команд, и systemd останавливается на первой
ошибке; для `derive`+`alerts` это правильно, потому что оповещать по
несвежим рёбрам хуже, чем не оповещать. Но `score` читает снимки и базовые
линии и с рёбрами не пересекается — сцепив их, вы получите: упал `derive`,
замолчали всплески, то есть тот вид оповещений, который даёт объём.

`baselines` — единственный тяжёлый проход: последние посты каждого канала и
медиана по зрелым постам сырого слоя, четырежды; около минуты. Сессию он не
держит и в то, что читает сбор, не пишет, так что рядом с `watch` безопасен —
ночное время здесь про диск, а не про корректность. Прерванный пересчёт
невидим, а не применён наполовину, поэтому его можно убивать без последствий.

Ежедневная частота — не гигиена. Канал сравнивается со своими последними
постами, и эта опора свежа ровно настолько, насколько свеж последний
пересчёт: раз в день против раза в неделю сужает сдвиг каналов с 0.19 до
0.15 z. Опора, которая не двигается, сравнивает выросший канал с ним самим
прежним — так было, пока она стояла с июля, и 72 канала из 229 сидели больше
чем на 1 z от нуля.

Первый пересчёт плейбук делает сам, но только если завершённых прогонов ещё
нет — повторный запуск плейбука тяжёлый проход не тянет.

## Если разворачиваете на ноутбук

```yaml
# deploy/group_vars/all/main.yml
host_is_laptop: true
```

Плейбук замаскирует `sleep.target`, `suspend.target`, `hibernate.target` и
`hybrid-sleep.target` и положит drop-in для logind, чтобы закрытая крышка
ничего не делала. В конце проверит, что `sleep.target` действительно
`masked`, и упадёт, если нет.

Это не гигиена. Уснувший коллектор не приостанавливается, а **теряет
снимки безвозвратно**: историю можно дособрать, а прочитать счётчики поста
в возрасте тридцати минут второй раз нельзя — пост больше не будет
тридцатиминутным. Ради этого `watch` и вынесен в отдельную фазу, и
закрытая крышка это молча отменяет.

Что остаётся руками — гашение засыпания по бездействию в GNOME. Через SSH
не сработает, нужен графический сеанс:

```bash
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-type 'nothing'
```

Строго говоря, маскировка целей это уже перекрывает — systemd не сможет
усыпить машину, о чём бы GNOME ни попросил. Команда выше просто убирает
бессмысленные попытки из журнала.

И держите ноут в розетке: на батарее всё вышеперечисленное отработает
ровно до разряда.

## Чего плейбук не делает намеренно

**Не запускает `itgraph login`.** Файл сессии копируется с рабочей машины,
потому что он несёт кэш сущностей, из которого `cached_peer` берёт пиров без
траты суточной квоты. На свежей сессии кэша нет: все seed-каналы уйдут в
«нет кэшированного пира», а восстановление через `resolve` при паре сотен
резолвов в сутки — трое суток остановленного сбора. Ловушка коварна тем, что
`login` выглядит как обычный шаг настройки.

**Не восстанавливает поверх непустой базы.** Единственный разрушительный шаг
защищён проверкой: если в `channels` есть строки, плейбук останавливается.
Перезапуск не должен быть способом потерять ручную разметку. Осознанно —
`-e force_restore=true`.

**Не гасит сбор на рабочей машине.** Это решение человека, и принимать его
стоит после того, как пройдёт проверка в конце.

## Что проверяется в конце

Три вещи, каждая ловит отказ, который иначе выглядит как успех:

| проверка | что ловит |
|---|---|
| в логе нет `Telegram route: direct` | `.env` не доехал, и коллектор ходит с адреса, который прокси должен был скрыть |
| в логе нет `no cached peer` | приехала не та сессия |
| `channels` со статусом `seed` не пусто | восстановление не легло |

Плейбук падает на любой из них — до того, как вы выключите рабочий сбор.

## Секреты

`deploy/group_vars/all/secrets.vault.yml` зашифрован ansible-vault и
**коммитится**: свежий клон приезжает с секретами, нужен только пароль.
Пароль лежит в `deploy/.vault_pass` (в `.gitignore`), `ansible.cfg` читает
его сам, поэтому `--ask-vault-pass` не нужен. Копия пароля — в менеджере
паролей; после клона:

```bash
pbpaste > deploy/.vault_pass && chmod 600 deploy/.vault_pass
```

Права `0600` — не формальность: исполняемый файл пароля Ansible не читает,
а **запускает** как скрипт.

**Репозиторий публичный, поэтому всё держится на пароле.** Шифротекст может
скачать кто угодно и подбирать пароль офлайн сколько угодно, а ключ
выводится всего десятью тысячами раундов PBKDF2. Пароль — только случайный
из генератора, от 20 символов; запоминаемый не годится. И смена пароля не
защищает старые коммиты: шифротекст каждой прежней версии остаётся в
истории. Если пароль утёк, менять нужно **сами секреты** — токен бота,
пароль прокси, пароли БД, — а не только пароль vault.

Правка — `ansible-vault edit deploy/group_vars/all/secrets.vault.yml`,
пароль подставится сам. Pre-commit не пропустит файл vault без заголовка
`$ANSIBLE_VAULT` и не пропустит `.vault_pass` даже через `git add -f`.

**Смена пароля — только с `--new-vault-id @prompt`:**

```bash
ansible-vault rekey --new-vault-id @prompt deploy/group_vars/all/secrets.vault.yml
pbpaste > deploy/.vault_pass        # новый, из менеджера паролей
```

Без флага `rekey` берёт старый пароль из `.vault_pass`, нового не
спрашивает, перешифровывает **тем же** паролем и пишет «Rekey successful».

`make ansible-lint` настоящий пароль не получает: ему подсовывается
заведомо фальшивый `deploy/.ansible-lint-vault-pass`, потому что без
какого-нибудь файла пароля Ansible не запускает даже `syntax-check`, а
расшифровывать линтеру нечего.

В `.gitignore` остаются:

```
deploy/inventory.ini
deploy/.vault_pass
deploy/group_vars/all/secrets.yml
```

**Postgres слушает только loopback**, и делается это в самом
`docker-compose.yaml`, а не оверрайдом. Оверрайд так не умеет: Compose
списки портов **дописывает**, а не заменяет, поэтому оверрайд добавлял
вторую публикацию того же порта — контейнер падал с «address already in
use», а широкий биндинг, который он собирался убрать, оставался на месте.

**Переменные лежат в каталоге `group_vars/all/`, а не двумя файлами рядом.**
Это не вкусовщина: `group_vars/<имя>.yml` задаёт переменные для **группы
инвентаря** с таким именем, поэтому файл `group_vars/secrets.vault.yml`
Ansible считает переменными группы `secrets.vault`. Такой группы нет — файл
молча не читается, и все секреты из него пропадают, а плейбук падает на
проверке «не найден telegram_api_hash». Внутри каталога `group_vars/all/`
имена файлов не значат ничего, и читается всё.

**Эндпоинт прокси лежит в секретах, а не в `main.yml`.** Он не просто
учётные данные: это адрес, с которого, как известно, ходит коллектор, —
ровно то, что прокси и существует скрывать, — а `all.yml` коммитится
открытым. Хост, порт, логин и пароль едут вместе, чтобы настройка прокси
была одной правкой в одном зашифрованном файле.

Файл сессии в репозиторий не попадает никогда: он в `.gitignore` по маске
`*.session`, а плейбук берёт его по пути с вашей машины.

## Отдельные части

```bash
ansible-playbook deploy/playbook.yml --tags services   # только unit-файлы и перезапуск
ansible-playbook deploy/playbook.yml --tags config     # только .env
ansible-playbook deploy/playbook.yml --tags laptop     # только запрет засыпания
ansible-playbook deploy/playbook.yml --tags verify     # только проверки
```

## Что остаётся руками

**Прокси.** Плейбук кладёт настройки (из `secrets.vault.yml`) и проверяет,
что маршрут не прямой, но сам эндпоинт вы получаете у провайдера VPN.
Проверить до запуска:

```bash
curl -s --socks5 ХОСТ:ПОРТ https://api.ipify.org
```

Адрес должен быть купленный, а не адрес виртуалки.

**Не заворачивайте весь трафик в WireGuard на удалённой машине** — полный
туннель меняет маршрут по умолчанию и рвёт вашу же SSH-сессию. SOCKS5 в
настройках гоняет через прокси только MTProto; SSH и Bot API идут напрямую,
и заблокировать себя так невозможно.

**Копии инвентаря.** 172 КБ, которые стоят недель разметки, и они не в дампе
отдельным файлом:

```bash
docker exec itgraph-postgres psql -U itgraph -d itgraph -c "\copy (
  SELECT tg_id, username, title, is_chat, status, kind, kind_note,
         reject_reason, reject_note, discovered_via, linked_to
  FROM channels) TO STDOUT WITH CSV HEADER" > ~/itgraph-inventory.csv
```
