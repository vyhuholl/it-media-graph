# IT-media graph
Аналитика айтишных телеграм-каналов: кто кого репостит, упоминает и комментирует.

## Требования
- [uv](https://docs.astral.sh/uv/) — Python-окружением управляет он, `python` и `pip` напрямую не используются
- Docker (для Postgres)
- `api_id` и `api_hash` с [my.telegram.org](https://my.telegram.org)

## Установка

```bash
uv sync
cp .env.example .env   # заполнить TELEGRAM_API_ID и TELEGRAM_API_HASH
```

### База данных

```bash
docker compose up -d          # Postgres на порту 5433
uv run alembic upgrade head   # накатить схему
```

Откатить схему на рабочей базе нельзя: `alembic downgrade` удаляет таблицы вместе с разметкой каналов, а URL берётся из окружения — то есть безопасная и разрушительная команды набираются одинаково. Поэтому откат разрешён только на одноразовой базе, чьё имя оканчивается на `_test`:

```bash
# посмотреть, что откат сделал бы, ничего не трогая
uv run alembic downgrade --sql head:base

# проверить миграцию на одноразовой базе
DATABASE_URL=postgresql+asyncpg://itgraph:itgraph@localhost:5433/itgraph_scratch_test \
  uv run alembic downgrade base
```

Если откат рабочей базы действительно нужен, сначала снимите копию (`make backup-full`), а затем разово выставьте `ITGRAPH_ALLOW_DESTRUCTIVE=1`.

### Резервные копии

Разметка каналов — это ручная работа, которую ничем не восстановить: канал можно перекачать заново, а решение «этот в скоуп, этот нет» нельзя. Поэтому копии снимаются двумя уровнями и **проверяются чтением** — файл, который не читается через `pg_restore`, копией не считается и не засчитывается.

| уровень | что | как часто | сколько хранится |
|---|---|---|---|
| `daily/` | `channels` + `backfill_state` | раз в 20 часов | 30 копий |
| `weekly/` | вся база, включая сырой слой | раз в неделю | 4 копии |

Копии лежат в `~/itgraph-backups`, вне репозитория: дамп содержит ваши подписки. Имена в UTC с суффиксом `Z` — дамп, снятый в 13:08 по Москве, называется `...T100802Z`.

```bash
make backup            # снять то, что назрело
make backup-full       # полный дамп прямо сейчас

make backup-install    # поставить агент launchd (раз в 4 часа)
make backup-status     # жив ли агент, с каким кодом завершился
make backup-log        # что он делал
make backup-uninstall  # снять агент; сами копии остаются
```

Агент запускается каждые 4 часа, а не в фиксированный час: на ноутбуке фиксированный час — это «когда крышка закрыта». Что именно снимать, решается по возрасту файлов на диске, поэтому лишние запуски ничего не стоят, а пропущенные из-за сна навёрстываются на следующем.

Кроме того, копия снимается автоматически перед каждым `alembic upgrade` на рабочей базе. Если копия не снялась, миграция не выполняется — обойти можно разовым `ITGRAPH_SKIP_BACKUP=1`.

#### Восстановление

Процедуру стоит прогнать хотя бы раз — непроверенное восстановление копией не является.

```bash
# развернуть копию в отдельную базу и посмотреть, что в ней
docker compose exec -T postgres psql -U itgraph -d postgres \
  -c 'CREATE DATABASE itgraph_restore_test'
docker compose exec -T postgres bash -c \
  'cat > /tmp/r.dump && pg_restore -U itgraph -d itgraph_restore_test --no-owner /tmp/r.dump' \
  < ~/itgraph-backups/weekly/full-XXXXXXXXTXXXXXXZ.dump
docker compose exec -T postgres psql -U itgraph -d itgraph_restore_test \
  -c 'SELECT status, count(*) FROM channels GROUP BY status'
```

Восстанавливать поверх рабочей базы имеет смысл только когда уже понятно, что именно потеряно: `pg_restore --data-only --table=channels` дольёт строки, не трогая схему.

### Авторизация в Telegram

Разовая операция. Сбор данных идёт через MTProto от лица обычного аккаунта, а не бота: Bot API не умеет читать историю каналов.

```bash
uv run itgraph login
```

Команда спросит номер телефона, код из Telegram и пароль двухфакторки, если он включён, и создаст файл сессии (`TELEGRAM_SESSION`, по умолчанию `itgraph.session`).

#### Если код не приходит

Для стороннего `api_id` Telegram присылает код **только сообщением в чат «Telegram»**, SMS не будет. Бывает, что сервер отвечает «отправлено», а сообщение так и не появляется — со стороны клиента это не чинится. Тогда есть вход по QR-коду, который обходит доставку кода целиком:

```bash
uv run itgraph login --qr
```

В терминале появится QR-код; на телефоне **Настройки → Устройства → Подключить устройство** → навести камеру. Токен живёт около полуминуты, команда перевыпускает его сама — сканировать нужно тот код, что сейчас на экране. Пароль двухфакторки, если он включён, спросят уже после сканирования. Результат тот же самый файл сессии, что и у обычного входа.

Не запускайте `login` повторно по кругу, если код не дошёл: неудачные попытки копятся на стороне Telegram и оборачиваются `FloodWaitError` на несколько часов.

**Файл сессии — это полный доступ к аккаунту.** Он в `.gitignore`; коммитить его нельзя ни при каких условиях. Все остальные команды только читают уже готовую сессию и никогда не спрашивают код: если сессии нет или она разлогинена, команда завершится с ненулевым кодом и отправит сюда.

## Инвентарь каналов

Ничего нельзя собирать, пока нет списка каналов, с которых собирать. Список берётся из собственных подписок и размечается вручную.

```bash
uv run itgraph dump-dialogs   # импорт публичных подписок
uv run itgraph channels       # сводка по статусам + весь список
uv run itgraph mark <tg_id|@username> --seed|--maybe|--reject ...
```

Канал адресуется либо числовым `tg_id`, либо username — с `@` или без, регистр не важен. Если username по какой-то причине числится сразу за двумя каналами (старый владелец ещё не переимпортирован), команда откажется угадывать и попросит указать id.

В инвентарь попадает только то, что публично адресуемо: каналы и супергруппы с username. Личные диалоги, старые групповые чаты (тип `Chat`) и каналы без username пропускаются — команда печатает только их количество, без названий. Приватная переписка в базу не попадает никогда.

`dump-dialogs` идемпотентен: при повторном запуске он обновляет username и название канала, но не трогает разметку. Каналы не удаляются никогда — отписка от канала не убирает его из инвентаря, а отклонённые каналы остаются в базе: это размеченные данные для будущего классификатора кандидатов.

### Цикл разметки

```bash
uv run itgraph dump-dialogs
uv run itgraph channels --status candidate

# айтишный канал автора о себе — берём в сиды
uv run itgraph mark 1234567890 --seed --kind personal

# лента вакансий — то же самое по username
uv run itgraph mark @example_jobs --seed --kind vacancies

# не про айти — отклоняем, причина обязательна
uv run itgraph mark 1234567892 --reject --reason crypto --note "торговые сигналы"

# непонятно, вернёмся позже
uv run itgraph mark 1234567893 --maybe

uv run itgraph channels        # сколько осталось неразмеченных
```

Значения `--kind`: `personal`, `aggregator`, `company`, `vacancies`, `media`, `community`, `event`. Это то, чем канал **является**, а не то, о чём он пишет.

Значения `--reason`: `not_it`, `adjacent`, `crypto`, `infobiz`, `ads`, `content_farm`, `other_scene`. К любой причине можно добавить `--note` свободным текстом.

## Сбор истории

Разметка отвечает на вопрос, с каких каналов собирать. `backfill` собирает — выкачивает историю сообщений в сырой слой.

```bash
uv run itgraph backfill --since 2026-01-01
```

Сохраняется **payload целиком, как пришёл**. Ничего не разбирается по дороге: репосты, упоминания, ссылки и язык вычисляются позже из этих же строк. Причина простая — разбор будет меняться много раз, а перекачивать историю ради исправления решения о разборе слишком дорого. Медиафайлы не скачиваются, сохраняются только метаданные из payload.

| опция | что делает | по умолчанию |
|---|---|---|
| `--since` | не запрашивать сообщения старше этой даты | обязательна |
| `--limit` | обработать не больше стольких каналов | все |
| `--delay` | пауза между запросами, секунды | 2.0 |
| `--batch-size` | сообщений за запрос | 100 |
| `--max-messages` | не больше стольких сообщений с одного канала — никогда, `0` — без потолка | 2000 |

Потолок `--max-messages` ограничивает канал, а не запуск. Без него несколько крупных новостных агрегаторов, постящих десятки раз в день, займут бо́льшую часть базы — и это самые неинформативные вершины графа: они репостят всех, а их не репостит никто. Достигнув потолка, канал закрывается **насовсем**: обход останавливается, и следующие запуски к нему не возвращаются, даже с более глубоким `--since`. Потолок считается по строкам в сыром слое, поэтому собранное в прошлые запуски тоже идёт в зачёт. В отчёте такие каналы считаются отдельно, как `capped`, а в `cutoff_at` записывается дата самого старого реально сохранённого сообщения, а не запрошенная в `--since`.

### Осторожный первый запуск

Полный проход по 200+ каналам — это несколько тысяч запросов и **часы работы**. Это первая команда проекта, которая обращается к Telegram в объёме, поэтому начинать нужно с малого:

```bash
# два канала, неглубоко — посмотреть, что вообще происходит
uv run itgraph backfill --since 2026-06-01 --limit 2

uv run itgraph channels --backfill   # что получилось
```

Убедившись, что всё разумно, можно постепенно поднимать `--limit` и опускать `--since`. Прерывать команду безопасно: прогресс каждого канала сохраняется вместе с сообщениями, которые он описывает, в одной транзакции — следующий запуск продолжит с того же места, а не начнёт заново.

Значения по умолчанию намеренно медленные. Ускорять `--delay` без причины не стоит: лимиты Telegram считаются на аккаунт, поэтому спешка ничего не выигрывает, а выглядит как бот.

### Как читать состояние

```bash
uv run itgraph channels --backfill
```

Последняя колонка показывает, докуда дошёл сбор:

| значение | смысл |
|---|---|
| `-` | канал ещё не трогали |
| `running` | идёт сейчас, либо прошлый запуск прервали |
| `complete to 2026-01-01` | история собрана до этой даты |
| `skipped` | не собирали и не из-за ошибки — например, нет username |
| `failed/permanent` | канал приватный, удалён или username больше не резолвится; повторно не запрашивается |
| `failed/transient` | сеть, таймаут, ошибка сервера; следующий запуск попробует снова |

Повторный запуск с той же датой пропускает уже собранные каналы. Запуск с **более ранней** датой не пропускает, а продолжает вглубь — поэтому окно можно расширять постепенно.

При `FloodWaitError` команда честно спит столько, сколько сказал Telegram, и повторяет тот же запрос. Другой сессии или аккаунта на этом пути нет ни в одной ветке: обход лимита — это то, что превращает ограничение в блокировку.

### Файл сессии стал дороже

Канал адресуется по `access_hash`, который выдаётся **на каждый аккаунт свой**. Инвентарь собран другим аккаунтом, поэтому его хэши здесь бесполезны — в базе хранятся только `tg_id` и username, а канал резолвится по username при первом обращении. Telethon кэширует результат в файле сессии.

Практический вывод: потеря `itgraph.session` **не теряет данные**, но заставляет резолвить каждый канал заново — то есть стоит одного медленного прохода. Резервных копий сессии не делайте: это полный доступ к аккаунту.

## Граф: репосты и упоминания

Сырой слой хранит сообщения целиком, но ничего в них не разбирает. `derive` строит из этих строк рёбра графа — кто кого репостит и упоминает, — а `resolve` добирает username и название каналам, найденным по ссылке. Это две разные команды, потому что операционно у них нет ничего общего: `derive` быстрый, повторяемый и **в сеть не ходит вообще**; `resolve` медленный, лимитируемый и несёт тот же риск для аккаунта, что и весь сетевой код проекта.

```bash
uv run itgraph derive     # построить рёбра из сырого слоя
uv run itgraph resolve    # дорезолвить найденные каналы (идёт в сеть)
uv run itgraph derive     # второй проход дописывает рёбра упоминаний
```

### Почему два прохода, а не один

Форвард несёт числовой id — это первичный ключ канала, поэтому и строку канала, и ребро можно создать сразу, в том же проходе. Упоминание несёт только `@username`: без id ни строки, ни ребра не создать. Такие username складываются в отдельную очередь (`pending_mentions`); `resolve` превращает их в каналы, и **следующий** `derive` дописывает рёбра. Рёбра упоминаний по построению отстают на один цикл, и граф достраивается за два-три чередующихся прохода: derive → resolve → derive. Это задумано так, а не ограничение, которое надо обходить.

`derive` **безопасно перезапускать в любой момент**: проход по неизменившимся данным не пишет ничего (рёбра вставляются с `ON CONFLICT DO NOTHING` по естественному ключу `источник + сообщение + тип + канал-цель + пост-цель`). Производные данные одноразовы — их всегда можно перестроить из сырого слоя, и именно поэтому эту часть дёшево ошибиться и дёшево итерировать, в отличие от сбора.

> **После миграции «post level forwards» таблица `edges` пуста — нужен один прогон `derive`.** Миграция добавляет в рёбра ссылку на исходный пост, а вставка идёт с `ON CONFLICT DO NOTHING`: дописать новые колонки в уже существующие строки такой вставкой нельзя — повторный `derive` посчитал бы их за конфликт и оставил колонки пустыми, отчитавшись об успехе. Поэтому миграция очищает `edges` целиком, и после `alembic upgrade head` граф восстанавливается одним `derive`. Сырой слой не трогается, перекачивать ничего не нужно; `pending_mentions` тоже остаётся на месте.

### derive

| опция | что делает |
|---|---|
| `--rebuild` | очистить `edges` и `pending_mentions` и построить заново. Единственный путь, удаляющий производные данные; `channels` и сырой слой он не трогает, поэтому канал, найденный форвардом, переживает `--rebuild`, а его рёбра просто перестраиваются |
| `--batch-size` | сообщений за партию (по умолчанию 1000) |

Что попадает в граф:

- **форвард из канала** → ребро `forward` к каналу-источнику. Ребро несёт и сам исходный пост: его id и дату первой публикации (`fwd_from.channel_post` и `fwd_from.date`). Форвард, не называющий исходного поста, всё равно даёт ребро — эти поля просто остаются пустыми. Форвард от пользователя, со скрытым источником (приватность автора) и репост канала самого себя — не рёбра: на том конце нет второго канала.
- **`@username` и ссылка `t.me/...`** → ребро `mention`. Ссылка на один пост (`t.me/name/123`, `t.me/c/<id>/<msg>`) несёт id этого поста; ссылка на канал целиком и обычное `@упоминание` — нет. Ссылка-приглашение (`t.me/joinchat/...`, `t.me/+...`), упоминание бота или человека, ссылка не на Telegram — не рёбра.
- одно сообщение, сославшееся на **один и тот же пост** дважды, даёт одно ребро; но две ссылки на разные посты одного канала — это два ребра, а форвард из канала и его же упоминание в том же сообщении — два ребра разных типов.
- **пересланный альбом** приходит несколькими сообщениями, у каждого свой `fwd_from`. Каждое даёт своё ребро, и все они несут общий id группы (`grouped_id`); derive их не схлопывает — свести альбом в одно событие это решение подсчёта, а оно относится к анализу, а не к разбору. `grouped_id` осмыслен только вместе с каналом-источником.

**Источники и цели.** Рёбра строятся только из каналов в статусе `candidate`, `seed` или `maybe`. Статусы перечислены явно, а не как «всё, кроме `rejected`»: когда в `channel_status` появится новое значение, его придётся включить или исключить осознанно — белый список уронит новый статус заметно (рёбра пропадут на следующем `--rebuild`), чёрный впустил бы его молча, а для таблицы, растящей инвентарь, шумный отказ безопаснее. Каналы-обсуждения (`is_chat`) источниками не служат, даже если их статус в списке: форвард внутри комментария — это репост человека, а не публикация чата. Каналы-**цели** не фильтруются: ребро к отклонённому каналу всё равно пишется — то, что сид репостит отклонённый канал, это факт о сиде.

**Отклонение вступает в силу только на `--rebuild`.** Обычный `derive` ничего не удаляет, поэтому рёбра канала, отклонённого уже после сбора, остаются на месте до следующего `derive --rebuild`, который очищает `edges` и строит их заново — уже без отклонённого источника. Сам инвентарь при этом не трогается: каналы, которые такой источник ввёл раньше (форвардом или упоминанием), остаются в `channels` со своим исходным `discovered_via`. Каналы вообще никогда не удаляются — `--rebuild` перестаёт добавлять новое, а не отменяет прошлое.

Время в пути — разница между датой исходного поста и датой репоста — намеренно не хранится: это вычитание двух колонок одной строки, и держать его в таблице наблюдений значило бы завести там первую производную величину. По той же причине альбом не схлопывается и никакие счётчики в рёбра не пишутся.

Персональные данные в граф не попадают: id пользователей из форвардов и подписанных постов отбрасываются на границе разбора и остаются в сыром слое, который никуда не экспортируется. Именно это оставляет производные таблицы безопасными для визуализации.

### resolve

Резолвит две очереди сразу: каналы, найденные форвардом (по id), и username из очереди упоминаний (публичным поиском). Подчиняется тем же правилам, что и `backfill`: последовательные запросы, пауза между ними, честное ожидание `FloodWaitError`.

| опция | что делает |
|---|---|
| `--limit` | не больше стольких запросов за запуск |
| `--delay` | пауза между запросами, секунды |
| `--retry-failed` | повторить и те ссылки, что не резолвились в прошлый раз |

Резолв канала по id требует `access_hash` — он выдаётся на каждый аккаунт свой и в сыром payload не хранится; Telethon кэширует его в файле сессии по мере сбора. Поэтому нерезолвящийся id — это промах кэша, а не приговор: следующий `backfill`, наткнувшись на тот же канал, может сделать его резолвящимся. Обычный запуск пропускает ранее упавшие ссылки, а `--retry-failed` пробует их снова — считать первую неудачу окончательной значило бы молча обрезать граф. Резолв username хэша не требует (это публичный поиск), поэтому у упоминаний этой проблемы нет.

То, что оказалось пользователем или ботом, а не каналом, канала не создаёт и записывается как таковое: граф хранит только каналы.

